    Project Scope¶

    What we're building and why

    Overview¶

    Crackz is a commercial AI-powered image analysis tool for detecting cracks in harbor and bridge infrastructure. It provides maritime engineers and infrastructure inspectors with automated crack detection to improve safety assessments and reduce manual inspection time.

    Business Goals¶

    Primary Objectives¶

    1. Automate crack detection in harbor concrete structures
    2. Reduce inspection time from manual visual inspection to automated analysis
    3. Improve detection accuracy with AI-powered segmentation models
    4. Enable enterprise deployment with Docker, GPU support, and team management
    5. Support offline operation for maritime environments with limited connectivity

    Success Criteria¶

    • Detection accuracy >85% IoU on validation sets
    • Processing speed <5 seconds per image on CPU
    • Memory usage <4GB RAM for standard workflows
    • Successful deployment to 5+ customer organizations
    • 95% customer satisfaction with detection quality

    Target Users¶

    Primary Users¶

    1. Harbor Inspection Engineers
    2. Need: Fast, reliable crack detection for routine inspections
    3. Pain point: Manual inspection is time-consuming and subjective

    4. Success: Reduce inspection time by 60%

    5. Infrastructure Managers

    6. Need: Historical tracking of crack progression over time
    7. Pain point: Inconsistent documentation across inspections

    8. Success: Reproducible project structure with versioned results

    9. Maritime Authorities

    10. Need: Compliance reporting with standardized detection metrics
    11. Pain point: Manual report generation from inspection photos
    12. Success: Automated reporting with PDF export and GPS mapping

    Secondary Users¶

    1. IT Administrators (enterprise deployment)
    2. Data Scientists (model training and tuning)
    3. Bridge Inspectors (similar use case to harbors)

    Core Features (Current)¶

    Project Management¶

    • ✅ Project scaffolding with reproducible directory structure
    • ✅ Image import with preprocessing (resize, organize splits)
    • ✅ Project migration for schema versioning
    • ✅ Clean command for maintenance (logs, artifacts)

    AI Pipeline¶

    • ✅ Training pipeline with PyTorch Lightning
    • ✅ Detection pipeline with batch processing
    • ✅ Model checkpointing and resumption
    • ✅ TensorBoard integration for training visualization
    • ✅ Runtime overrides (epochs, batch size) without YAML edits

    User Interfaces¶

    • ✅ CLI (Typer): Primary interface for automation and CI/CD
    • ✅ GUI (CustomTkinter): Desktop app for visual project management
    • ✅ Docker: Three variants (full, slim, GPU) for enterprise deployment

    Deployment & Operations¶

    • ✅ Docker images with multi-stage builds
    • ✅ Azure Batch support for distributed processing
    • ✅ Azure VM deployment scripts (CPU and GPU)
    • ✅ Hybrid logging (central + per-project)
    • ✅ GPS/EXIF support with interactive maps and GeoJSON export

    Integration¶

    • ✅ MCP (Model Context Protocol) for AI assistant integration
    • ✅ Shell completion (bash, zsh, fish, PowerShell)
    • ✅ GitHub Actions CI/CD workflows
    • ✅ GitHub Copilot optimization

    Constraints¶

    Technical Constraints¶

    1. Python 3.11+ minimum (3.13 recommended for performance)
    2. PyTorch ecosystem (switching ML frameworks not feasible)
    3. YAML-based config for human readability (no binary configs)
    4. Backward compatibility for project schemas (must support migration)
    5. Offline-first design (no required internet connectivity)

    Performance Constraints¶

    1. Memory: Must run on laptops with 8GB RAM (4GB allocated)
    2. CPU speed: <5 seconds per image on modern Intel/AMD CPUs
    3. GPU training: Support CUDA 11.8+ and 12.x
    4. Container startup: <30 seconds cold start
    5. Test coverage: Minimum 75% (enforced in CI)

    Business Constraints¶

    1. Commercial licensing: GPL-3.0 source-available model
    2. Enterprise deployment: Must support air-gapped environments
    3. Customer support: Email support within 24 hours
    4. Data privacy: No telemetry, no cloud-required features
    5. Stability: No breaking changes without major version bump

    Development Constraints¶

    1. CI/CD: All tests must pass on GitHub Actions
    2. Code quality: Ruff linting, mypy type checking enforced
    3. Documentation: All public APIs must be documented
    4. Performance: No regressions >20% without justification
    5. Git workflow: No direct pushes to main, all changes via PR

    Non-Goals¶

    Explicitly Out of Scope¶

    1. Real-time video detection (focus on still images)
    2. 3D reconstruction (2D segmentation only)
    3. Mobile-first UI (desktop and CLI focus)
    4. Multi-user collaboration (single-user project management)
    5. Cloud storage integration (local storage only)
    6. Third-party API dependencies (self-contained operation)

    Why These Are Out of Scope¶

    • Real-time video: Harbor inspections use high-res still photos, not video
    • 3D reconstruction: Not required by customers, adds complexity
    • Mobile-first: Harbor engineers use laptops/tablets with keyboards
    • Multi-user collaboration: Single inspector per project is current workflow
    • Cloud storage: Customer data privacy requirements favor local storage
    • Third-party APIs: Offline operation is critical for maritime environments

    • Test Coverage: >75% line coverage, >80% target

    • Inspection Time Reduction: 50%+ reported by users
    • Support Response Time: <24 hours for email support
    • Documentation Coverage: 100% of CLI commands documented

    Development Metrics¶

    • Release Cadence: Minor releases every 2-3 weeks
    • Issue Resolution Time: <7 days for bugs, <30 days for features
