    Graphify for Agents¶

    This document explains how agents (Claude, other AI models) can use the Crackz knowledge graph to understand architecture and make better decisions.

    Quick Start for Agents¶

    1. Query the Graph Directly¶

    # Agent: "Understand what ModelRegistry does"
graphify explain "ModelRegistry"

# Agent: "How does training work?"
graphify query "trace the training pipeline"

# Agent: "Should mask editing be in GUI or CLI?"
graphify path "masks_cli" "MaskEditorDialog"

    2. Use Query Shortcuts¶

    # Run common queries without MCP
./scripts/graphify-queries.sh god-nodes
./scripts/graphify-queries.sh architecture
./scripts/graphify-queries.sh cli-gui-boundary
./scripts/graphify-queries.sh training-pipeline
./scripts/graphify-queries.sh surprising

# See all available queries
./scripts/graphify-queries.sh list

    3. MCP Server (Structured Tool Calls)¶

    Start the server: 

    ./scripts/mcp-server.sh start

    Agents can then call these tools programmatically:

    Tool: query_graph
Input: "What does the Project class do?"
Output: [subgraph with explanation]

Tool: get_node
Input: "ModelRegistry"
Output: {id, label, connections, file location}

Tool: shortest_path
Input: {source: "MainWindow", target: "AIChatService"}
Output: [edge chain showing path]

Tool: god_nodes
Output: [top 10 highest-connectivity nodes]

Tool: get_community
Input: 0
Output: [all 54 nodes in community 0]

    Architecture Insights for Agents¶

    God Nodes (Most Connected Abstractions)¶

    ModelRegistry (79 edges) - Controls all model lifecycle (creation, loading, checkpointing) - Central bottleneck—all model work flows through here - Agent tip: Before adding model features, check if ModelRegistry should handle it

    QtAppState (63 edges) - GUI state management - Used by all views for reactive updates - Agent tip: For GUI features, mutations go through QtAppState

    MainWindow (62 edges) - Top-level container, orchestrates all panels - Agent tip: New tabs/panels registered here

    AIChatService (57 edges) - LLM integration (chat, embedding, inference) - Agent tip: For AI features, implement here or call AIChatService

    Project (46 edges) ⚠️ Chokepoint - Configuration hub—spans 23 communities - Agent tip: High coupling risk—consider splitting

    Surprising Connections (Refactoring Targets)¶

    CLI→GUI Violation - masks_cli.py imports MaskEditorDialog from GUI - Violates layer separation (CLI shouldn't know about GUI) - Agent recommendation: Abstract through a service layer

    Test→Core Tight Coupling - Tests import internal functions, not just public APIs - Makes refactoring risky - Agent recommendation: Enforce test→public API only

    Project Spans 23 Communities - Indicates over-responsibilities - Agent recommendation: Split into ProjectConfig, ProjectMetadata, ProjectImport

    Communities (Tight Coupling Zones)¶

    Community Purpose Nodes Cohesion
    0 Annotation config 54 0.04
    1 Database layer 33 0.04
    2 Training pipeline 25 0.04
    ... ... ... ...

    Agent tip: Code in the same community is tightly coupled. Avoid creating dependencies between communities.

    Using Graph Data in Code Decisions¶

    Example 1: Where Should New Feature Go?¶

    Agent question: "I need to add a new model type. Where in the codebase?"

    Graph exploration: 

    graphify explain "ModelRegistry"
graphify query "what creates models?"
graphify path "MainWindow" "ModelRegistry"

    Output: ModelRegistry is the central hub for all models. New types should register there.

    Example 2: Is This Coupling a Problem?¶

    Agent question: "Should CLI call GUI? They're in different layers."

    Graph exploration: 

    graphify path "masks_cli" "MaskEditorDialog"
graphify query "what other CLI->GUI calls exist?"

    Output: This is a known surprise connection—indicates missing abstraction layer.

    Example 3: Can I Refactor This?¶

    Agent question: "Project is coupled to everything. Can I safely split it?"

    Graph exploration: 

    graphify explain "Project"
graphify query "what depends on Project?"
graphify get_community 38  # Project's community

    Output: Project has 46 edges across 23 communities. Safe refactoring: extract ProjectConfig (used for initialization), ProjectMetadata (runtime info), ProjectImport (data loading).

    MCP Integration for Claude Desktop¶

    If using Claude Desktop, add to ~/.config/Claude/claude_desktop_config.json:

    {
  "mcpServers": {
    "graphify": {
      "command": "python3",
      "args": ["-m", "graphify.serve", "/absolute/path/to/graphify-out/graph.json"]
    }
  }
}

    Then Claude can query the graph while coding: 

    [Claude is now connected to Graphify tools]
Claude: "Before I add this feature, let me query the graph..."
[Claude automatically calls query_graph, shortest_path, etc.]

    Keeping Graph Current¶

    Auto-update on commits: 

    git commit -m "feat: add new model type"
# Post-commit hook runs automatically
# Graph updated with new code

    Manual update after big refactor: 

    ./scripts/graphify-queries.sh surprising  # See new surprises
graphify . --update                        # Re-extract changed files
./scripts/mcp-server.sh restart            # Restart for agents

    Common Agent Queries¶

    "Understand the architecture"¶

    ./scripts/graphify-queries.sh all
    Output: God nodes, main components, surprising connections

    "Where should this go?"¶

    graphify explain "TargetModule"
graphify path "CurrentLocation" "TargetModule"
    Output: Community membership, distance, dependencies

    "Is this coupled?"¶

    graphify query "what connects X to Y?"
    Output: All paths, edge confidence, source files

    "What's a good design pattern?"¶

    graphify query "how do other modules do X?"
    Output: Similar code patterns from other communities

    "Can I refactor this?"¶

    graphify explain "ClassToRefactor"
graphify query "what depends on ClassToRefactor?"
    Output: All dependents, refactoring risk assessment

    Performance Tips for Agents¶

    1. Start with god nodes 

      graphify explain "ModelRegistry"  # Fast, high-value overview

    2. Use path queries for specific flows 

      graphify path "A" "B"  # Direct, focused answer

    3. Query before implementing

    4. Ask graph: "Does this pattern exist elsewhere?"

    5. Copy similar implementation, avoid inventing new patterns

    6. Check surprising connections before refactoring 

      ./scripts/graphify-queries.sh surprising

    7. Unexpected edges often indicate hidden requirements

    8. Use communities to scope changes 

      graphify get_community 0  # See all tight-coupled code

    9. Changes within a community have less cross-community impact

    Troubleshooting¶

    MCP server not starting? 

    ./scripts/mcp-server.sh status
tail -20 /tmp/graphify-mcp.log

    Graph out of date? 

    graphify . --update
./scripts/mcp-server.sh restart

    Query returns empty? 

    # Verify node exists
graphify query "what modules exist?"
# Try exact node name
graphify explain "ModelRegistry"
