    ADR-030: Backend Topology — One Crackz Backend, Many Clients, On-Prem First¶

    Status: Proposed

    Date: 2026-11-12

    Context¶

    Crackz started as a client application: the Qt GUI and the CLI run on the user's computer and call crackz.app services in-process. Integrating with survey-tool needs a reachable, server-hosted Crackz. survey-tool's ADR-017 (Proposed, 2026-11-12) sets the direction: survey-tool pulls from Crackz; Crackz is stateless for inference; no job or status endpoints. Its ADR-013 calls cloud "an optional, later, single-tenant target". Crackz defers cloud for a reason of its own: a cloud Crackz would have to fetch original images across the site boundary from an on-prem survey-tool.

    Already built under epic #828 / #824 (all on main):

    • crackz.serve (FastAPI): POST /detect (image by URL), POST /detect/upload (multipart), GET /health; the versioned contract schema_version "1" (serve/contract.py).
    • Per-caller bearer keys (SHA-256 hashes, two keys per caller for rotation, per-caller origin allowlist) and an SSRF-gated fetcher (serve/auth.py, serve/fetch.py).
    • A Detector protocol: the route works before the real model loader exists (#821, #643).

    Still undecided, and what this ADR settles: who the callers are, what state the backend owns, how humans sign in, and how the web GUI the project wants (React, same shape as survey-tool, with Authentik) relates to the Qt app and to the existing API. Decided by the project owner on 2026-11-12: the web GUI is React; the Qt client app stays as it is. Multi-tenancy is a separate issue.

    Decision¶

    1. One backend process per install, one single-tenant Postgres. crackz serve is the backend. It owns the install's models, datasets and runs in the install's own database (ADR-023, ADR-025: federation by HTTP contract, never a shared DB; no tenant_id). Placement (laptop, on-prem server, later cloud) is deployment configuration, not code. On-prem first; cloud is deferred because it needs original images to leave the site.

    2. Three kinds of caller, two route families, one app.

    Caller Route family Credential
    survey-tool, surface-ops (machines) Inference API: /detect, /detect/upload, /health. Stateless, contract v1. Shipped. Scoped bearer key (per caller)
    React web GUI (humans) Project API: projects, datasets, runs, models. Stateful, backed by crackz.app services and crackz.db repositories. New. User sign-in (OIDC, below)
    Qt desktop app, CLI Local in-process by default, as today. May optionally use the project API (#830) with a user credential. User sign-in or local

    The inference API stays stateless and unchanged: the project API is additive and lives under its own prefix (/api/v1, proposed) so the machine contract's paths never move. Both are versioned; there are no ad-hoc endpoints. The presentation layer (crackz.serve) calls crackz.app and never touches the database itself (decision 6).

    1. Two authentication paths that never mix.
    2. Machines: bearer keys as shipped (#841). Hash-only storage, constant-time compare, fail closed, /health open for probes, origin allowlist per caller. A user token is not accepted on the inference routes, and a service key is not accepted on the project API.
    3. Humans: OIDC authorization-code + PKCE from the browser against the install's Authentik (a public client, no secret). Crackz validates the access token as a resource server: RS256 only, signature against the issuer's JWKS, and iss, aud, exp and a non-empty sub checked. Roles come from a roles claim of group names that Crackz maps to its own roles; Crackz owns authorization and does not trust the claim for per-object access. This mirrors survey-tool's approach deliberately, so one Authentik can serve both products. The shape comes from survey-tool's code (survey_core/auth/tokens.py, ops_portal_ui/src/auth/oidc.ts), not from its ADR-015, which settles only OIDC-in-app, Authentik, and roles mapped to capabilities by the app; the token-validation details are proposed here. Tokens live in browser memory, not local storage. Details (audience, group names, claim mapping) are #831.

    4. Never: a GUI user authenticates as a user, not with survey-tool's key, and no client is ever given a credential into survey-tool. Crackz sends no credential when it fetches an image (a pre-signed, expiring URL on an allowlisted origin is the only access it gets).

    5. The web GUI is a new React application beside Qt, not a replacement. Stack follows survey-tool's apps/ops_portal_ui (React 18, Vite, TypeScript, react-router, TanStack Query; no third-party UI kit found). It lives in its own top-level directory, separate from the Python packages, and is served as static files by the reverse proxy. Unlike survey-tool's hand-written API client, TypeScript types should be generated from Crackz's OpenAPI document so the client cannot drift from the contract. The Qt app is untouched by this decision; the Streamlit dashboard is left alone and revisited only when the web GUI covers its use.

    6. Deployment shape (detail in #832): a reverse proxy terminates TLS, serves the static web app and forwards API calls; crackz serve binds to loopback or an internal network; callers and keys come from a mounted callers file; Postgres is the install's own. Non-loopback binding without a callers file is refused by the crackz serve command (shipped; create_app itself does not enforce it).

    7. Database access follows survey-tool's layering rules (its .importlinter contract 11, invariants and ruff TID251), adapted to Crackz's packages:

    8. Layers: routes (crackz.serve) -> services (crackz.app) -> repositories (crackz.db) -> driver and ORM. A route never imports sqlalchemy, a driver, crackz.db, or a first-party re-export of them, and never holds a session: it receives values or a service object, and the session is opened inside crackz.app / crackz.db. survey-tool learned this the hard way: a re-export module let routers hold a live AsyncSession (its #1896), because its contract is keyed on names and sees only direct imports. Any module that re-exports persistence is added to the list.
    9. survey-tool enforces it three ways: an import-linter forbidden contract (allow_indirect_imports = true, since the legitimate chain is indirect), a ruff TID251 banned-api, and an AST guard for imports inside function bodies. Its TID251 is repo-wide and works through a long per-file allowlist; Crackz has no tidy-imports configuration, so it would need path scoping to serve or is dropped in favour of the other two.
    10. Crackz today: contract 13 / DB_OWNER already forbids sqlalchemy, psycopg, psycopg2, asyncpg and alembic everywhere except crackz.db, crackz.serve included. Missing is only crackz.serve -> crackz.db itself (an import-linter contract) and the function-body AST guard. Both are follow-ups before the project API gets its first route.
    11. The inference API holds no connection (it is stateless). The project API reaches the database only through crackz.app, one engine per process from CRACKZ_DATABASE_URL (ADR-023).

    12. Never run a DB-backed command or migration against a default environment that may point at a live database (survey-tool AGENTS.md); Crackz makes migration operator-only (#844). The gap on the test side is noted in decision 7.

    13. Test setup follows survey-tool's tiers (its docs/testing.md). Crackz already has the core of it: the DB fixtures pg_engine and pg (and an autouse migrated-schema fixture) live only in core/tests/integration/crackz/conftest.py, so a unit test cannot see them, and the root conftest.py marks everything under integration/ as integration. (tmp_project exists in both tiers with different meanings; unit tests define their own without a database.) For the backend that means:

    14. Unit tier (core/tests/unit/crackz/serve/): no database, no network, no Docker. Routes are tested with FastAPI's TestClient against a fake Detector and, for the project API, a stubbed crackz.app service layer (survey-tool: "mock the queries layer"). This is how the inference API is tested today.
    15. Integration tier (core/tests/integration/): real Postgres through pg_engine, the app built over a real session. Marked integration, skipped when no database is reachable.
    16. To add: an AST guard that no unit-tier test or conftest requests a DB fixture (survey-tool's test_unit_tier_has_no_db_fixtures.py: drift left tests running in neither tier). Derive the fixture names from the integration conftest, but key on the DB ones (pg_engine, pg), not on every name, because tmp_project is legitimately shared; and note that CLI integration tests reach the database through the autouse fixture without naming one, which a name-based guard cannot see. Also an architecture-contract test for the layering in decision 6, including imports inside function bodies, and a check that every test root is in testpaths (a Crackz addition; survey-tool's testing guide does not describe one).
    17. Gap to close: pg_engine defaults CRACKZ_DATABASE_URL to the local dev database with os.environ.setdefault and runs alembic upgrade head against whatever URL is set. That is the live-database risk survey-tool's rule exists for, and the setdefault also leaks into later tests. Integration tests should require an explicit test URL.

    18. Conventions to copy: patch with monkeypatch.setattr, never swap sys.modules; a test that changes settings environment variables clears the settings cache before and after. Similarity tests already set hnsw.ef_search explicitly (test_embeddings_postgres.py), the HNSW counterpart of survey-tool's ivfflat.probes advice.

    19. Out of scope here: multi-tenancy, served-model management (#833), image and artifact storage (#845), the graphical installer (#847), and the real model loader (#821, #643).

    Consequences¶

    • Benefit: the machine contract survey-tool builds against does not move while the human-facing API is designed; each side can ship independently.
    • Benefit: one identity provider for both products, and the same token-validation shape, so the survey-tool code can be a reference rather than a dependency.
    • Requirement, not yet built: the key/user separation holds today only because require_caller does a hash lookup. The project API needs its own dependency per router, a test that each credential type gets 401 on the other family, and generic 401 wording (the current message names a "bearer key"). The shared global exception handlers are part of this.
    • Benefit: Qt users are not forced onto a server; the web GUI is purely additive.
    • Trade-off: two route families and two auth schemes in one app; the separation must be enforced (distinct dependencies per family) and tested, or a key could reach a user route.
    • Trade-off: a second frontend technology (TypeScript) enters a Python repository: build, lint and CI for it are new work.
    • Trade-off: the project API duplicates some crackz.app operations as HTTP; what is remote first is decided in #830, not here.
    • Trade-off: serve calling crackz.app can pull heavy dependencies (torch) into the API process. The inference process loads them anyway; keep imports lazy so /health and the contract stay light.
    • Open (decide in the issues named, not here): where project, dataset and run state lives when a remote client creates it (the install's Postgres is the intent; per-project SQLite files remain for local mode) and how the two meet; per-object authorization (#831); how the project API is versioned (a path prefix is proposed; the inference contract's schema_version rule is the model); whether /docs and /openapi.json stay open for it; same-origin serving through the reverse proxy so the SPA needs no CORS; and the #738 import and similar-defect API, which belongs to the project family.
    • Follow-up: #831 (JWT validation, roles, audience), #830 (remote mode), #832 (packaging and proxy), #833 (model management), and a web GUI issue once the first screens are chosen.

    Alternatives Considered¶

    • Extend the Streamlit dashboard into the multi-user UI. Rejected: server-rendered, no OIDC integration, and cannot share survey-tool's frontend architecture, which the project wants.
    • Replace Qt with the web GUI. Rejected by the project owner (2026-11-12): the client app stays as is.
    • One credential type (service keys for humans too). Rejected: per-user identity and revocation need a real identity provider, and sharing a machine key with people would break attribution and rotation.
    • Forward-auth at the proxy only (Authentik outpost) with no token validation in Crackz. Rejected for the API: survey-tool treats it as a stopgap (ADR-015 phase 0; OIDC-in-app is its phase 1), and a service that trusts headers is only as safe as its network. Acceptable later as an extra layer, not as the only one.
    • Cloud-hosted first. Rejected for now: Crackz would have to fetch originals across the site boundary, and survey-tool's ADR-013 itself treats cloud as a later, optional target.
