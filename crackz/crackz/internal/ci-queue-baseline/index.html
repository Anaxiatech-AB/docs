    CI queue baseline and merge-queue assessment (#788, #789)¶

    Queue = job started_at - created_at; run = completed_at - started_at. Jobs that were skipped or cancelled are left out of every figure (a skipped job reports a near-zero run and queue). scripts/ci_queue_stats.py computes the tables below from gh api .../actions/runs/<id>/jobs.

    Two measurements, and only one can be reproduced.

    • Snapshot, 2026-11-03 (the tables labelled "Snapshot"): 406 jobs of pull_request runs created after 2026-10-25 (the run count was not recorded). Quoted as recorded. The run records behind it no longer exist: the API lists no pull_request run created between 2026-10-26 and 2026-11-11 (16 runs of other events, while 39 PRs merged in that window: gh pr list --state merged --search 'merged:2026-10-26..2026-11-11' --limit 200), so these figures cannot be re-derived and the script cannot reproduce the "Before" window. The script that produced them also counted skipped jobs, so the recorded queue and run p50s are probably too low.
    • Re-measurement, 2026-11-13 (the tables labelled "Re-measured"): the hosted-runner window the API still holds (runs created 2026-11-12 and 2026-11-13), produced by the script as committed, which leaves skipped and cancelled jobs out. A measurement taken right after a config change is a timestamp, not a steady state: re-run it before relying on it.

    Two things did not improve:

    • architecture-review went from 11 s to 44 s p50, probably a cold start on a hosted runner (no warm cache). Not investigated; the job is small.
    • Unit Tests failures (2/40 after, 0/24 before). One traced: run 41530241768, a failure in test_config_categories_cli.py, a test file new in that PR, so a PR bug and not the runner. The other ran on a different runner and its log could not be recovered (the run no longer shows as failed, likely re-run or superseded), so its cause is unknown. Neither is a confirmed hosted-runner failure.

    Not measured: hosted-minute cost (the self-hosted runner was not billed; about 350 runner-minutes were used in the first day after the switch), and any window longer than about one day.

    Findings against the proposed work¶

    • Item 2/3, classification before allocation. Every workflow filters inside the job (dorny/paths-filter, then if: ... unit == 'true' on later steps), so a skipped suite still allocates a runner. On hosted runners that cost ~10 s of queue plus the checkout in the snapshot (queue p95 is 3 s in the re-measurement). 20 of 41 Documentation Build jobs finished in under 30 s. Moving the filter to a separate changes job would add a job and a checkout per workflow and would not remove the required status, so the saving is seconds. No workflow change is proposed: the failure mode (a skipped required check never reporting) is worse than the cost, and the in-job filter already reports a stable status and runs everything on any non-pull_request event.
    • Item 4, cache comparison. Not run, deliberately: it needs a persistent runner (the cited ~177 s venv restore was on one), and hosted runners start cold. With total CI at about 5 min there is nothing to buy. Re-run it if the self-hosted pool returns, keeping the rollback below.
    • Item 5, AI review contention. architecture-review ran 15 times, 12 runner-minutes total in the snapshot (29 runs, 20 min in the re-measurement), and no longer contends because nothing queues.
    • Item 6. No continue-on-error added; #762 untouched.

    Rollback / re-queue trigger¶

    Set the variable back to the self-hosted pool recorded in the earlier version of this note (the variable's previous value was not kept, so confirm it before relying on it):

    gh variable set CRACKZ_SELF_HOSTED_RUNNER_LABELS --body '["self-hosted","foto-dator"]'

    (docs/ci-runners.md describes the mechanism but still uses radiogaga as its example host, so the two documents disagree; tracked in #873.) Re-open the optimisation if hosted-minute cost becomes the constraint or the self-hosted pool is restored: then item 2 (a changes job) and item 4 (cache A/B) are worth re-measuring.

    Merge-queue assessment (#789)¶

    Decision: no-go for now. The #788 baseline exists and the starvation that motivated the question is resolved; a merge queue would not add value at today's throughput and would break required checks as configured.

    Compatibility audit (required contexts on main: Lint and Type Check, Integration Tests, Documentation Build, Unit Tests (3.13)):

    • unit-tests.yml and integration-tests.yml trigger on pull_request and workflow_dispatch, build.yml on pull_request; docs.yml on push to main (docs paths only), pull_request, workflow_run (after Release), a weekly schedule and workflow_dispatch. None has a merge_group trigger, so in a queue the required contexts would never be reported and every merge group would wait for a status that cannot arrive.
    • The step-level filters gate on github.event_name == 'pull_request', so under merge_group they would take the != branch and run the full suite. That is fail-closed for test selection, which is the desired direction.
    • docs.yml also has a job-level if: that admits only push, pull_request, workflow_dispatch and a successful workflow_run. Under merge_group the whole Documentation Build job would be skipped, and a skipped job does not report the required context. Adding the trigger is not enough: the if: must accept merge_group too. The other three workflows have no job-level event gate (checked).
    • ai-architecture-review.yml is pull_request with paths:; it is not a required context and need not run on merge_group.
    • concurrency groups use github.ref; whether merge-group refs collide with cancel-in-progress has not been tested and belongs in the pilot.

    Minimal plan if this is later approved (not activated here): add merge_group: (types [checks_requested]) to the four required workflows, keep the != 'pull_request' full-run branches, set queue build concurrency 1 and group size 1 for the pilot, and keep the four contexts unchanged. Rollback: disable the rule on main; the extra merge_group: triggers are inert without it.

    Post-merge signal: 20 failed push runs on main between 2026-04-24 and 2026-06-15 (Unit, Integration, Build, Docs). Those workflows no longer run on push: on current main only docs.yml does (and only for docs paths), so a break that lands on main in the other three is not visible post-merge. One consequence reaches past CI signal: release.yml starts from workflow_run of Integration Tests on branch main, and that workflow now runs only on pull requests, so the automatic release path has not fired since 2026-06-16 (#872). Titles of those runs show release bumps, dependabot batches and known flakes; none was attributed to a semantic conflict between two green PRs, but that attribution was not done run by run. Treat the rate as an upper bound on merge-caused breakage and re-assess if it recurs.

    Reproduce¶

    uv run python scripts/ci_queue_stats.py

    Needs an authenticated gh, run inside the repository. It reads up to 400 pull_request runs created on or after 2026-10-25, the jobs of each (latest attempt, all pages), and the last 100 merged PRs, then prints the aggregate, per-job and PR tables above, plus the run range it read and how many jobs it left out. The tables here are its "after" columns, reformatted with units (and days for the long PR tails); the script prints seconds and minutes. It warns when the 400-run limit ends before the window start. It takes about three minutes. Because the API no longer holds the runs from 2026-10-26 to 2026-11-11, the "Before" window comes out nearly empty: only the 2026-11-12 onward figures can be regenerated.
