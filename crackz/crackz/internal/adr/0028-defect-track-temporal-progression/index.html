    ADR-028: Defect Track Temporal Progression (B-minimal)¶

    Status: Accepted

    Date: 2026-06-15

    Context¶

    Phase 1 (#627/#653, ADR-023) gave crackz pgvector-backed visual similarity search. Phase 2 (#661, ADR-027) added GPS-filtered ranking via a filter-then-blend SQL query (search_with_gps) and shipped the embedding_temporal_weight config key inert at 0.0 for Phase 3 to activate.

    Phase 3 (#662) takes the first slice: temporal progression — letting an inspector see how one physical defect evolved across separate inspection runs. The data model has no concept of defect identity across inspections: every detection_results row is independent, and the only signals for "this June crack is the same crack as in March" are visual similarity (DINOv2 cosine distance), GPS proximity (geom/gps_latitude/gps_longitude), and inspection time (detection_runs.run_at). Each signal has gaps:

    • Visual similarity false-matches look-alike cracks, and a worsening defect drifts visually — the case we most care about is the one matching defeats.
    • GPS is frequently NULL because foto-dator is underwater — a normal mode, not an edge case (established in ADR-027).
    • Inspection time orders runs but says nothing about identity.

    A stored, correctable representation of defect tracks is also the substrate the future anomaly-evolution slice will need, so deferring to query-only history would require rebuilding it later.

    Three design options were considered:

    • Option A (implicit query): history = on-demand similarity search grouped by run_at, nothing persisted.
    • Option B-minimal (chosen): a stored defect_tracks identity table, auto- proposed links the inspector can confirm/reject, and a dedicated ProgressionView. Full curation UI deferred.
    • Full Option B: B-minimal + complete split/merge/reassign curation UI in the same slice.

    Decision¶

    B-minimal: a thin stored defect_tracks identity table, auto-proposed links (visual similarity + optional GPS tiebreak) via an idempotent track link command, and a ProgressionView for display.

    Data model¶

    defect_tracks is deliberately thin — pure identity:

    column type notes
    id BigInteger PK, Identity
    project_id BigInteger FK → projects.id ON DELETE CASCADE indexed
    created_at TIMESTAMPTZ server_default=now()

    Severity, category, confidence, GPS, and time all live on detection_results/detection_runs and are derived by joining. Duplicating them on the track would cause drift.

    Track membership and link metadata are added to detection_results (one detection belongs to at most one track):

    column type notes
    track_id BigInteger FK → defect_tracks.id ON DELETE SET NULL, nullable NULL = unlinked
    track_link_status Text, nullable proposed / confirmed / rejected
    track_link_cosine Double, nullable raw pgvector <=> cosine distance [0,2] that justified the proposal
    track_link_distance_m Double, nullable GPS distance (m) at proposal time; NULL when GPS absent

    track_link_cosine stores raw cosine distance (the pgvector <=> convention); the similarity used for threshold comparison is derived as 1 - distance/2, matching ADR-027.

    Migration 0004: run_at TEXT → TIMESTAMPTZ¶

    detection_runs.run_at is the chronological sort key for the whole feature. Keeping it TEXT in a temporal feature is a liability. Every existing value is written as UTC ISO-8601 (datetime.now(UTC).isoformat() in detection_runner; mtime.isoformat() in app/projects), so the cast is safe:

    ALTER TABLE detection_runs ALTER COLUMN run_at TYPE TIMESTAMPTZ USING run_at::timestamptz;

    Blast radius (updated together in this migration): db/models.py (run_at Mapped[str] → Mapped[datetime]), db/records.py DTO fields, read sites in metrics_store.py, repositories/geo.py, repositories/detections.py, cli/geo_cli.py, sqlite_import.py, and integration test assertions comparing run_at to literal ISO strings.

    Settings (new, config/crackz_settings.py, embedding_* convention)¶

    • embedding_track_sim_threshold: float = 0.85 — minimum cosine similarity to propose a link. Both are Field(ge=0.0).
    • embedding_track_radius_m: float = 50.0 — GPS inclusion radius (metres) for the tiebreak. Matches the example radius used throughout the #661 design.

    Matching rule (auto-linker, Python-only — no PostGIS dependency)¶

    For each detection with an embedding (current model_name + embedding_version):

    1. Find the best candidate in other runs where visual_similarity ≥ embedding_track_sim_threshold (visual_similarity = 1 - cosine_distance / 2, the ADR-027 convention).
    2. When both sides have GPS, additionally require distance_m ≤ embedding_track_radius_m; rank candidates by proximity as a tiebreak. When either side lacks GPS (underwater), fall back to visual-only — the GPS clause is skipped, not failed.
    3. Transitive grouping (union-find): if A↔B and B↔C both match, A, B, C share one track, not three. Pairwise matches collapse into a single defect_tracks row.

    The linker loads every project embedding for the current model/version once, then computes pairwise cosine similarity (dot product, L2-normalised vectors) and the GPS tiebreak (Haversine) entirely in Python with a union-find collapse. It does not call search_with_gps, does not use ST_DWithin, and has no PostGIS dependency. This is O(n²) in detections-per-project; acceptable for B-minimal. Blocking/ANN candidate generation is noted as a future optimisation.

    Idempotency¶

    propose_links (the repository function that drives track link) is idempotent: re-runs touch only proposed/unlinked rows and reuse the existing proposed track for a group (no duplicate defect_tracks rows are created). Confirmed links are never overwritten; rejected stays rejected unless explicitly reset.

    Layering¶

    GUI/CLI → service (ai/embedding/service.py or ai/tracking/: link_tracks, history_for_detection, confirm, reject, TrackHistory value object) → repository (db/repositories/tracks.py: propose_links, confirm_link, reject_link, track_history) → DB.

    Service and repository import neither Typer nor Qt, matching the Phase 2 seam discipline. The service is also the REST seam for the future #643 endpoint.

    Known limitation¶

    A worsening defect that drifts visually below embedding_track_sim_threshold will not be auto-linked, and B-minimal has no manual-add UI yet (split/merge/ reassign are deferred to the anomaly-evolution slice). This is a known limitation, documented openly here rather than hidden.

    Consequences¶

    • Benefit: Inspectors gain a durable, correctable record of defect identity across runs — confirmed links survive re-embedding and CLI re-runs.
    • Benefit: The linker is PostGIS-independent (pure Python + Haversine), so GPS tiebreak works on any Postgres deployment and has no degrade path to manage.
    • Benefit: ProgressionView + track history CLI surface the full inspection timeline including visual drift (cosine of each member vs the earliest member).
    • Benefit: The thin defect_tracks table is the stored substrate the anomaly-evolution slice will need; deferring it would require rebuilding it then.
    • Trade-off: O(n²) pairwise linking is acceptable for B-minimal project sizes but will need blocking or ANN candidate generation as projects grow.
    • Trade-off: A worsening defect that drifts below the similarity threshold is not auto-linked and cannot yet be corrected manually (no split/merge UI).
    • Trade-off: embedding_temporal_weight stays inert this slice; a history is a grouping by time, not a re-ranking. The weight stays at 0.0 until the dedicated ranking slice.
    • Follow-up: split/merge/reassign curation UI → anomaly-evolution slice.
    • Follow-up: embed-time auto-link hook (standalone track link ships first for link-correctness validation).
    • Follow-up: activating embedding_temporal_weight as a ranking term → separate Phase 3 slice.

    Alternatives Considered¶

    • Option A (ephemeral query-only history): History = on-demand similarity search grouped by run_at, nothing persisted. Fastest to implement, but a "track" is ephemeral, cannot be corrected, cannot represent a worsening defect, and would need to be rebuilt as a stored entity for anomaly-evolution anyway. Rejected.
    • Full Option B (B-minimal + complete curation UI this slice): Adds split/merge/reassign UI in the same work unit. Too large for one plan; curation UI is deferred to the anomaly-evolution slice. Rejected for scope.
    • PostGIS-based linker (ST_DWithin in SQL): The Phase 2 search_with_gps approach uses ST_DWithin inside the HNSW scan for per-query ranking. All-pairs linking across a project is a different shape (grouping, not ranking), so pushing it into SQL gains little and adds a PostGIS degrade path to manage. Haversine in Python with union-find is simpler and equally correct at B-minimal scale. Rejected.
