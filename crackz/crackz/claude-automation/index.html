    Claude Code Automation Guide¶

    Claude Code is configured with a layered automation stack for this project: MCP servers that give Claude live access to external data, hooks that run automatically on every edit, subagents that act as specialist reviewers, and skills that package repeatable workflows into slash commands.

    This document describes every piece, when to use it, and how the parts compose into end-to-end workflows.

    MCP Servers¶

    MCP servers extend Claude with tools that reach outside the codebase. Configured in .mcp.json; takes effect after restarting Claude Code.

    context7¶

    Fetches live documentation for any library — no stale training-data guesses.

    Use it by: mentioning the library in your prompt.

    use context7 — how does smp.Unet() handle the encoder_weights param?

    Claude calls context7 automatically when you ask about external libraries (PyTorch, SMP, PySide6, Albumentations, etc.).

    codegraph¶

    A tree-sitter-parsed structural index of the entire codebase. Sub-millisecond lookups for definitions, call graphs, and impact analysis.

    When to prefer codegraph over grep:

    Question Tool
    Where is BackendSpec defined? codegraph_search
    What calls training_runner? codegraph_callers
    How does detection reach the report? codegraph_trace
    What breaks if I rename IoUMetric? codegraph_impact
    Give me context for a training task codegraph_context

    The index auto-syncs after every Python edit to core/src or gui/src (via the PostToolUse hook). If it ever gets stale, run codegraph sync . manually.

    Crackz-specific prebuilt queries (via scripts/codegraph-queries.sh):

    ./scripts/codegraph-queries.sh architecture
./scripts/codegraph-queries.sh training-pipeline
./scripts/codegraph-queries.sh gui-state
./scripts/codegraph-queries.sh model-lifecycle

    Hooks¶

    Hooks fire automatically — no invocation needed. All hooks are async (non-blocking) except the two PreToolUse guards.

    PreToolUse — Protected file guard¶

    Fires before every Edit or Write. Blocks edits to:

    • .env — secrets
    • uv.lock — managed by uv, not manual edits
    • .pre-commit-config — commit hook config
    • data/, outputs/, logs/ directories
    • Model weight files: .ckpt, .pt, .pth, .safetensors

    If Claude attempts to edit a protected file, the operation is rejected with an explanation.

    PreToolUse — Force-push guard¶

    Fires before every Bash command. Blocks git push --force (or -f) targeting main. Redirects to a PR instead.

    PostToolUse — Ruff lint + format (async)¶

    After every Python file edit: runs ruff check --fix and ruff format on the saved file. Silently auto-fixes style issues.

    PostToolUse — mypy type-check (async)¶

    After every edit to a file under core/src or gui/src: runs mypy on that file. Errors surface in Claude's next response.

    PostToolUse — Related unit tests (async)¶

    After every edit to core/src/crackz/**/*.py: looks for a corresponding test at core/tests/unit/**/*_test.py (same path structure) and runs it with pytest --tb=short. Fast feedback on regressions without running the full suite.

    PostToolUse — YAML validation (async)¶

    After every .yaml / .yml edit: pipes the file through yaml.safe_load to catch syntax errors immediately. Training config typos are caught before they reach the GPU.

    PostToolUse — Architecture boundary lint (async)¶

    After every edit to core/src or gui/src: runs lint-imports --quiet. Catches violations of the client/backend boundary (e.g. gui importing directly from core.db).

    PostToolUse — CodeGraph sync (async)¶

    After every Python edit to core/src or gui/src: runs codegraph sync . in the background (suppressed console window). Keeps the structural index fresh after every change.

    Stop — Session diff summary¶

    When Claude finishes a session: runs git diff --name-only HEAD and prints the list of files changed. Gives a quick summary of what the session touched.

    Subagents¶

    Subagents are specialist Claude instances with scoped tools, a focused system prompt, and sometimes a specific model. Invoke them by name in your prompt, or they are spawned automatically by skills like /pr-review.

    ml-config-reviewer (Opus)¶

    Audits training configuration files before GPU runs. Checks:

    • Learning rate ranges per backbone type (SMP vs SegFormer)
    • Loss function suitability for class-imbalanced crack detection
    • Augmentation safety for thin-crack morphology
    • Batch size / VRAM fit
    • Backbone name validity (SMP encoder registry, SegFormer HuggingFace IDs)
    • Scheduler params consistency
    • Early stopping patience
    • Checkpoint path specified

    When to use: Before launching any training run. Also invoked automatically by /train-model.

    use ml-config-reviewer — check core/configs/train_segformer_b3.yaml

    benchmark-guard (Sonnet)¶

    Runs pytest -m benchmark --benchmark-compare and explains regressions. Saves a baseline if none exists. Flags any benchmark with >20% mean or >30% max regression.

    When to use: Before pushing changes that touch the training loop, inference pipeline, data loading, or IoU/Dice computation.

    use benchmark-guard — I just refactored the IoU computation

    qt-thread-safety-reviewer (Opus)¶

    Audits Qt/PySide6 code for thread safety violations. The hard rule: all UI mutations must happen on the main thread.

    Checks: - Direct widget access from QThread.run() bodies - Qt.DirectConnection across threads - time.sleep() blocking the main event loop - Object ownership and lifetime bugs

    When to use: Before merging any code that touches QThread, workers, or async callbacks that update the UI.

    use qt-thread-safety-reviewer — gui/src/crackz_gui/qt/views/detection_view.py

    qt-signal-auditor (Sonnet)¶

    Audits signal/slot connections for memory leaks and double-connect bugs. Checks:

    • Lambda captures that create reference cycles
    • Signals connected in __init__ with no corresponding disconnect() in cleanup
    • connect() inside loops or repeatedly-called methods (fires N times)
    • Missing @Slot decorators on cross-thread slots

    When to use: When adding new views or wiring up new signals.

    security-reviewer (Opus)¶

    Security audit focused on ML inference and config loading patterns. Checks:

    • torch.load() without weights_only=True (pickle RCE vector)
    • yaml.load() without SafeLoader (arbitrary object instantiation)
    • Path traversal in user-supplied file paths
    • subprocess.run(shell=True) with interpolated input
    • Hardcoded API keys or credentials
    • eval() / exec() on config-derived strings

    When to use: Before merging any code that loads models, reads user-supplied paths, parses configs, or calls subprocess. Also invoked automatically by /pr-review.

    developer¶

    General implementation agent. Reads project conventions from docs/agent-playbook.md and applies them when writing code.

    pytorch-expert¶

    Deep learning specialist. Use for questions about training loop correctness, gradient flow, device placement, mixed precision, or SMP/SegFormer architecture choices.

    docker-specialist¶

    Docker build and multi-variant image questions (cpu / cu118 / cu128 variants, the scripts/build_cuda_wheels.py build matrix).

    docs-writer¶

    MkDocs Material documentation. Use when writing or updating docs/.

    reviewer¶

    Lean code reviewer. Fast, minimal, high-signal. For quick checks on a function or class before committing.

    Skills (slash commands)¶

    Skills are slash commands that package multi-step workflows. Type /skill-name in the Claude Code prompt to invoke.

    /run-coverage¶

    Runs uv run task coverage, reads reports/coverage.json, and lists every module below 80% statement coverage with the first 5 missing lines. Ends with an offer to generate tests for the gaps.

    /run-coverage

    /check-ci¶

    Gets the current branch, finds its PR, runs gh pr checks, fetches logs for any failing run (gh run view --log-failed), and outputs a pass/fail table with the single most actionable fix.

    /check-ci

    /pr-review¶

    Parallel review: spawns ml-config-reviewer, qt-thread-safety-reviewer, and security-reviewer concurrently on the current branch's diff. Merges all three verdicts into a single report.

    Files are automatically routed: - core/src/crackz/ai/** and *.yaml → ML reviewer - gui/src/crackz_gui/** → Qt reviewer - All .py + YAML → security reviewer

    /pr-review

    Output:

    ## PR Review: feat/my-branch
### ML Config Review     — PASS / ISSUES FOUND
### Qt Thread Safety     — SAFE TO MERGE / NEEDS FIXES
### Security Review      — SAFE TO MERGE / NEEDS FIXES
### Final Verdict        — READY TO MERGE / BLOCKED

    /new-feature¶

    The primary workflow for starting any non-trivial feature. Orchestrates the full development lifecycle from idea to merged PR:

    Step What happens
    1. Spec Creates docs/superpowers/specs/YYYY-MM-DD-<name>-design.md with overview, file changes, and acceptance criteria
    2. ADR Creates a new ADR file from docs/internal/adr/template.md and links it from docs/internal/adr/02-decisions.md — only if architecture changes are involved
    3. Worktree git worktree add .worktrees/<name> -b feat/<name> — isolated workspace, nothing bleeds into main
    4. Task list Creates docs/superpowers/plans/YYYY-MM-DD-<name>.md — 3–7 checkbox tasks, each ending with a passing test + commit
    5. Implement Works through each task using the developer agent for larger changes
    6. Tests uv run task tests + uv run task lint — stops if red
    7. Review Runs /pr-review — parallel ML + Qt + security review
    8. PR gh pr create with generated description 
    /new-feature

    Prompts for: feature name, one-paragraph description, whether architecture changes are involved.

    Output: 

    Spec:      docs/superpowers/specs/2026-05-27-<name>-design.md
Plan:      docs/superpowers/plans/2026-05-27-<name>.md
ADR:       docs/internal/adr/<NNNN-title>.md (if applicable)
Worktree:  .worktrees/<name>
Branch:    feat/<name>
PR:        https://github.com/…/pull/<N>

    /new-model-backend¶

    Scaffolds a new SMP or HuggingFace segmentation backend. Asks for the name, type, and backbone identifiers, then:

    1. Reads base.py + smp.py as templates
    2. Creates backends/<name>.py with the correct BackendSpec
    3. Registers in __init__.py before SMP_SPEC (SMP must stay last as catch-all)
    4. Adds a unit test
    5. Runs pytest core/tests/unit/ai/model/
    /new-model-backend

    /add-qt-view¶

    Scaffolds a new PySide6 view or dialog. Asks for the name and type, picks the closest existing view as a template, creates the file, exports it, optionally wires a service, and adds a stub test.

    /add-qt-view

    /add-cli-command¶

    Scaffolds a new Typer subcommand. Asks for the name and purpose, reads the existing CLI structure, creates the command file with typed options and structured logging, registers it in the entry point, and adds a unit test.

    /add-cli-command

    /train-model¶

    End-to-end training pipeline:

    1. Locates training configs — asks if multiple
    2. Spawns ml-config-reviewer — stops if any ❌ critical issue
    3. GPU preflight: checks CUDA availability, dataset paths, unit tests
    4. Runs uv run crackz train --config <path>
    5. Evaluates IoU + Dice from the latest checkpoint
    6. If IoU ≥ 0.75 and Dice ≥ 0.80: creates feat/model-<backbone>-iou<X.XX> branch and commits the checkpoint
    /train-model
# or with a specific config:
/train-model core/configs/train_segformer_b3.yaml

    /release¶

    Pre-release readiness gate — checks everything before you touch release.yml:

    1. Warns if not on main or if working tree is dirty
    2. Runs uv run task tests — stops on failure
    3. Checks CI: latest unit-tests + integration-tests runs must be green
    4. Runs cz bump --dry-run — shows proposed version bump
    5. Shows commits since last tag + CHANGELOG unreleased section
    6. Lists artifacts the pipeline would build (cpu/cu118/cu128 wheels, GUI wheel, sdist, PDF if minor/major)
    7. Outputs GO / NO-GO verdict and the exact gh workflow run command if ready
    /release

    Composed Workflows¶

    Everyday coding loop¶

    The hooks handle everything automatically:

    Edit a Python file
  → ruff fixes style (async)
  → mypy checks types (async)
  → related unit test runs (async)
  → codegraph syncs (async)

    No manual steps needed. Check the next Claude response for any type errors or test failures.

    Before pushing a PR¶

    /pr-review          # parallel ML + Qt + security review
/run-coverage       # check for coverage gaps
/check-ci           # verify CI is green on the branch

    Starting a new feature end-to-end¶

    /new-feature
# prompts for name, description, architecture changes?
# → creates spec + ADR (if needed) + worktree + task list
# → implements, tests, reviews, opens PR automatically

    This is the primary entry point for non-trivial work. For smaller scaffolding tasks, use the dedicated skills below.

    Adding a new model architecture¶

    /new-model-backend             # scaffold the backend
use ml-config-reviewer         # review the training config for it
/train-model                   # validate config → train → auto-branch on success
use benchmark-guard            # verify no perf regression vs baseline
/pr-review                     # full parallel review before PR

    Adding a new GUI view¶

    /add-qt-view                          # scaffold the view
use qt-thread-safety-reviewer         # review if it uses workers
use qt-signal-auditor                 # check signal/slot wiring
/pr-review                            # full review before merging

    Releasing a new version¶

    /release            # go/no-go + shows exact gh command
# If GO:
gh workflow run release.yml -f confirm=YES
# After release completes, manually trigger if needed:
gh workflow run pyinstaller-build.yml
gh workflow run docker-build.yml

    Configuration Files¶

    File Purpose
    .mcp.json MCP server definitions (context7, codegraph)
    .claude/settings.json Hooks (PreToolUse guards, PostToolUse async pipeline, Stop summary)
    .claude/settings.local.json Permissions allowlist (uv, git, gh, codegraph, WebSearch)
    .claude/agents/*.md Subagent definitions — 10 specialists
    .claude/skills/*/SKILL.md Skill definitions — 9 slash commands
    CLAUDE.md Project root context — commands, agents, skills index
    .claude/CLAUDE.md Scoping hints — which paths to scan per task type, CodeGraph cheatsheet
    .github/CLAUDE.md CI context — workflow names, CI conventions

    Permissions allowlist (.claude/settings.local.json)¶

    Claude can run the following without prompting:

    Bash(uv:*)         — all uv commands
Bash(codegraph:*)  — codegraph sync/serve
Bash(git:*)        — all git operations
Bash(gh:*)         — GitHub CLI
Bash(node:*)       — Node/npx (for context7 MCP)
Bash(QT_QPA_PLATFORM=offscreen uv run:*)  — headless Qt tests
WebSearch          — web lookups

    Everything else prompts for permission.

    Adding a new hook¶

    Edit .claude/settings.json. Use "async": true for any hook that doesn't need to block the edit:

    {
  "type": "command",
  "command": "python -c \"...\"",
  "statusMessage": "Running ...",
  "async": true
}

    Windows-specific: use creationflags=0x08000000 in subprocess.Popen to suppress console windows. Use shutil.which() rather than hardcoded binary paths.

    Adding a new subagent¶

    Create .claude/agents/<name>.md with YAML frontmatter:

    ---
name: my-agent
description: One sentence — used by Claude to decide when to invoke it.
tools: Read, Grep, Glob     # restrict to what it actually needs
model: sonnet               # or opus for complex reasoning
---

Agent instructions here...

    Then add the name to CLAUDE.md and .claude/CLAUDE.md.

    Adding a new skill¶

    Create .claude/skills/<name>/SKILL.md:

    ---
name: my-skill
description: One sentence summary.
---

# Steps

1. ...
2. ...

    Then add /name to the Skills section of CLAUDE.md.
