    ADR-029: Assisted Classification (Confirmed-Pool Suggestion)¶

    Status: Accepted

    Date: 2026-06-16

    Context¶

    Issue #662 (Embeddings Phase 3, under #627) has four acceptance criteria. The historical progression view shipped in PR #684 (ADR-028, merged 2026-06-15). Three remain: clustering, assisted classification, and anomaly evolution. This ADR covers the assisted-classification slice only.

    Assisted classification: when a new defect is visually close to known verified defects, suggest a likely class, a severity estimate, and related cases — with the inspector always verifying and approving. The AI suggests only; it never writes a classification back.

    The existing data model has no dedicated "verified" flag and no inspection-records table separate from detection_results. What #684 added is track_link_status ∈ {proposed, confirmed, rejected} on detection_results, representing an inspector's approval of a temporal link between runs. That is the only human-in-the-loop signal currently available.

    Decision¶

    Verified pool = detections with track_link_status = 'confirmed'. This reuses #684's human-in-the-loop signal with no new table and no migration.

    Search filter¶

    The existing search() in db/repositories/embeddings.py uses an HNSW index with hnsw.iterative_scan = strict_order to avoid the filtered-recall problem when a tight metadata filter would otherwise starve results below top_k. A new optional confirmed_only: bool = False parameter restricts the scan to track_link_status = 'confirmed' via an EXISTS subquery against detection_results, keeping the driving scan on defect_embeddings — the same shape as search_with_gps — so the HNSW iterative-scan recall path is preserved. The query's own row is excluded post-search by detection_result_id in the service layer (tolerant of absence, following the existing search_by_detection pattern).

    Output¶

    suggest_classification() in ai/embedding/service.py returns a ClassificationSuggestion with:

    • Suggested class (primary_category): cosine-similarity-weighted vote over confirmed neighbours, skipping NULL-category neighbours.
    • Single suggested severity (defect_severity or crack_severity): defect_severity and crack_severity are populated identically in the multiclass workflow; we vote once using each neighbour's defect_severity or crack_severity, mirroring the existing pdf_exporter.py fallback.
    • Related cases: the confirmed neighbour SearchHit list.
    • A "k of n agreed" support count per label (k = neighbours voting for the winning value; n = neighbours with a non-NULL value for that field).
    • A min-support floor (default 2): a label whose n < min_support is suppressed and reason="insufficient_support" is set, but related cases are still returned. A (1, 1) agreement built on a single sample is not surfaced as a suggestion.

    Suggest-only¶

    The service never writes a category or severity back. Applying a suggestion is the inspector's existing detection-edit action, out of scope here.

    Surface¶

    • CLI: crackz classify suggest <detection_result_id> [--top-k 10] [--min-support 2] in a new cli/classify_cli.py, registered in cli/crackz_cli.py.
    • GUI: a read-only SuggestionView (BaseView subclass) wired into detection_gallery_widget.py, data loaded off the UI thread following the same worker pattern as ProgressionView.

    Honest limitation¶

    track_link_status = 'confirmed' means an inspector approved a temporal link between runs — that the June detection and the March detection are the same physical defect. It does not mean the detection's class or severity was independently verified. The voted labels are the same segmentation model's primary_category / defect_severity that produced the query detection, and a confirmed row can even have primary_category = NULL.

    This feature is precedent retrieval among human-vetted recurring defects, not a verified ground-truth label store. The value is "here are visually similar defects an inspector found worth tracking, and what the model called them" — surfaced for the inspector to judge, never auto-applied. This limitation must be communicated clearly wherever the feature is documented or surfaced.

    Consequences¶

    • When a real verified-classification store lands (e.g. a dedicated inspection-records table as anticipated in #627), it supersedes the confirmed-pool proxy. The confirmed_only search filter and the similarity-weighted vote are reusable unchanged.
    • No new table, no migration. The SearchHit dataclass gains defect_severity and crack_severity fields (NULL on non-confirmed paths); GpsSearchHit inherits them and the GPS search path is unaffected.
    • Clustering and anomaly evolution — the other two #662 criteria — are separate future slices. This ADR and its PR do not close #662.

    Alternatives Considered¶

    • Dedicated verified-classifications / inspection-records table (separate from detection IDs, per #627): this would be the proper future home for inspector-verified labels and would supersede the confirmed-pool proxy. Rejected for now as premature / YAGNI at this slice.
    • Python-side filtering after a broad top-N search (fetch top-N, filter confirmed in Python): the filtered-recall problem bites exactly when confirmed defects are rare (early adoption); a fixed top_k can return zero confirmed neighbours. Rejected.
    • Numeric confidence model: more complex and no more honest than a support count when the pool is small. The "k of n" indicator is simpler and transparent. Rejected.
