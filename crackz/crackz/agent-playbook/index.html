    Agent Playbook¶

    Shared repo-level guidance for Codex, GitHub Copilot, and Claude Code in Crackz.

    Goal¶

    Keep project guidance in the repository and keep user-level configuration personal. Use this file as the source of truth for project-specific agent behavior.

    Quick Start¶

    Read in this order unless the task is extremely narrow:

    1. CONTEXT.md
    2. PLAYBOOK.md
    3. This file
    4. Relevant focused docs:
    5. docs/architecture-guidelines.md
    6. docs/03-tasks.md
    7. PRODUCT_ROADMAP.md

    Project Standards¶

    • Use Python 3.13 conventions already present in the repo.
    • Use uv for package management and execution. Do not use pip or conda.
    • Use uv run task ... for standard workflows where a task exists.
    • Use typer.secho() for end-user CLI output and logger from crackz.log for technical output.
    • Reuse centralized CLI options from core/src/crackz/cli/options.py.
    • Use pathlib.Path and keep code/tests platform-agnostic.
    • Prefer minimal, focused changes over broad refactors.
    • Add or update tests when behavior changes.
    • Lazy imports in the GUI: heavy libraries (PIL, numpy, diskcache, torch) must be imported inside the function or method that first needs them, never at module level in GUI entry-point modules (app.py, app_state.py, views, panels). This keeps startup fast. Use TYPE_CHECKING blocks for type annotations that reference these types.

    Git Workflow Default¶

    • Start code, docs, and CI changes on a branch, then push the branch and open a pull request.
    • Do not commit directly to main unless the user explicitly instructs you to do so.
    • When addressing PR feedback or follow-up fixes, continue working on the same branch associated with that PR unless the user explicitly asks to use a different branch.
    • Treat direct pushes to main as an exception that requires explicit user instruction.

    Worktrees¶

    • Prefer a separate git worktree when it helps keep unrelated local changes untouched.
    • Use a worktree for parallel branch work, PR follow-up fixes, or review tasks that should not disturb the current working tree.
    • Do not create a worktree by default; use one when it clearly reduces risk, context switching, or branch confusion.
    • If using a worktree, keep ownership clear: one branch per worktree, and do not mix unrelated tasks in the same worktree.

    Protected Files¶

    Treat these as protected unless the task explicitly requires changing them:

    • .env
    • uv.lock
    • .pre-commit-config*

    Validation Ladder¶

    Run the smallest relevant checks first.

    1. Targeted lint/format for touched Python files:
    2. uv run ruff check --fix <path>
    3. uv run ruff format <path>
    4. Targeted type check when signatures or public APIs changed:
    5. uv run mypy <path>
    6. Targeted tests for changed behavior:
    7. uv run pytest <test>
    8. Broader tasks only when warranted:
    9. uv run task tests
    10. uv run task integration
    11. uv run task build_docs

    Push Readiness¶

    • Before pushing, run the smallest relevant validation for the change using the Validation Ladder.
    • This typically includes targeted Ruff checks and formatting, targeted mypy when signatures or public APIs changed, and the appropriate unit tests for affected behavior.
    • Do not push changes that have not been validated at an appropriate scope unless the user explicitly instructs you to do so.

    Role Map¶

    Use the Crackz-specific repo skills in .agents/skills when the task clearly matches:

    • crackz: default entry skill for general Crackz repository work
    • crackz-developer: general implementation, bug fixes, and small refactors
    • crackz-reviewer: focused review for bugs, regressions, and missing tests
    • crackz-docs-writer: docs and docstring work
    • crackz-docker-specialist: Dockerfiles, image variants, registry/CI container work
    • crackz-pytorch-expert: training, inference, metrics, and model pipeline work

    Repo Vs User Level¶

    Keep these in the repository:

    • Project conventions and coding rules
    • Crackz-specific workflows
    • Role-specific skills tied to this codebase
    • Shared references and architecture context

    Keep these at user level:

    • Personal trust settings
    • Local permissions and command allowlists
    • Personal plugins/connectors
    • Generic cross-repo skills you want everywhere
    • Secrets, tokens, auth state, machine-specific paths

    Effective Setup By Agent¶

    Codex¶

    • Reads AGENTS.md
    • Uses repo skills from .agents/skills
    • May also use personal skills from ~/.codex/skills

    GitHub Copilot¶

    • Reads .github/copilot-instructions.md
    • Uses repo skills from .agents/skills
    • Uses personal skills from ~/.copilot/skills

    Claude Code¶

    • Reads CLAUDE.md
    • Uses Claude-specific repo config in .claude/
    • May also use user settings in ~/.claude/

    Claude supports extra repo-local hooks and agent definitions. Those are useful, but they are not portable. For Codex and Copilot, prefer expressing the same behavior in repo docs and repo skills.

    Default Operating Style¶

    • Read only the files needed for the task plus nearby interfaces.
    • Avoid full-repo scans unless the task actually requires them.
    • Do not change unrelated files.
    • Prefer direct execution over long planning for small tasks.
    • For larger tasks, make a short plan and then execute.
    • Summaries should be concise and include changed files, why they changed, and what was verified.
