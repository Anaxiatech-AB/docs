    ChromaDB: Vector Database Fundamentals¶

    What is ChromaDB?¶

    ChromaDB is an open-source vector database specifically designed for AI applications. It stores and searches vector embeddings to identify semantically similar information. ChromaDB is optimized for RAG (Retrieval-Augmented Generation) workflows where language models need relevant context from large document collections.

    Core Concept: Instead of storing text directly, ChromaDB converts documents into high-dimensional vectors (embeddings) that capture semantic meaning. Similar concepts cluster together in vector space, enabling fast similarity search.

    Key Features & Capabilities¶

    Developer-First Design¶

    • Simple Python API: 3 lines to get started
    • Zero configuration: Works out-of-the-box for prototyping
    • Flexible embeddings: Supports OpenAI, Sentence Transformers, Cohere, or custom models
    • Multi-modal: Handles text, images, and other data types

    Performance (2025 Update)¶

    • Rust-core rewrite: 4x performance improvement over previous versions
    • Billion-scale: Handles billions of embeddings in cloud mode
    • Sub-millisecond queries: Fast retrieval for small-medium datasets
    • HNSW indexing: Hierarchical Navigable Small World graphs for efficient nearest-neighbor search

    Search Capabilities¶

    • Vector similarity: Cosine distance, L2 distance, or inner product
    • Full-text search: Traditional keyword-based search
    • Metadata filtering: Filter by document properties before similarity search
    • Hybrid search: Combine vector and keyword search

    Architecture¶

    ChromaDB offers three deployment modes:

    1. Embedded Mode (Development)¶

    import chromadb

# Runs entirely in-process, no separate server
client = chromadb.Client(Settings(
    persist_directory="./chroma_data"
))

    Characteristics: - Zero infrastructure overhead - SQLite-based local persistence - Perfect for development and small datasets (<1M vectors) - Runs in the same process as your application

    2. Client-Server Mode (Production)¶

    import chromadb

# Connect to separate ChromaDB server
client = chromadb.HttpClient(host="localhost", port=8000)

    Characteristics: - Separate server process for scalability - Multiple clients can connect - Better resource isolation - Supports horizontal scaling

    3. Managed Cloud Mode (Enterprise)¶

    • Fully managed service with auto-scaling
    • High availability and backup
    • No operational overhead
    • Pay-per-use pricing

    Storage Technology¶

    Three-Tier Storage: 1. In-Memory Cache: Hot data for sub-millisecond access 2. Local Persistence: SQLite for embedded mode, RocksDB for server mode 3. Distributed Storage: Cloud object storage (S3, GCS) for massive scale

    Indexing: - Uses HNSW (Hierarchical Navigable Small World) graphs - Optimized for high-dimensional spaces (typical: 384-1536 dimensions) - Approximate nearest neighbor (ANN) search with tunable accuracy/speed tradeoff

    Neo4j: Graph Database Fundamentals¶

    What is Neo4j?¶

    Neo4j is a native graph database that stores data as nodes, relationships, and properties. Unlike traditional databases that treat relationships as foreign keys, Neo4j makes relationships first-class citizens with the same status as entities. This enables efficient traversal of complex, interconnected data.

    Core Concept: Data is a graph: entities are nodes, connections are relationships. Queries traverse this graph to answer questions like "How is A connected to B?" or "What's the shortest path from X to Y?"

    Key Features & Capabilities¶

    Cypher Query Language¶

    Neo4j uses Cypher, a declarative graph query language similar to SQL but optimized for pattern matching.

    Example Query: 

    // Find best encoder for low-light harbor images
MATCH (tr:TrainingRun)-[:USES_MODEL]->(m:Model),
      (tr)-[:TRAINED_ON]->(ds:Dataset)-[:CONTAINS_IMAGE]->(img:Image),
      (tr)-[:PRODUCED_CHECKPOINT]->(ckpt:Checkpoint)
WHERE img.exif_iso > 800  // Low-light condition
  AND ds.domain = "harbor"
RETURN m.encoder,
       AVG(ckpt.val_iou) as avg_iou,
       COUNT(tr) as num_runs
ORDER BY avg_iou DESC
LIMIT 5

    As of 2025: - Cypher 5: Frozen, only bug fixes (backward compatibility) - Cypher 25: Active development, new features monthly

    Native Graph Storage¶

    • Index-free adjacency: Relationships stored physically with nodes
    • O(1) relationship traversal: No expensive joins
    • Pointer-based navigation: Traverse millions of hops in milliseconds

    ACID Compliance¶

    • Full transactional support
    • Consistency guarantees
    • Rollback on failure
    • Isolation levels configurable

    Rich Graph Algorithms¶

    Built-in algorithms for: - Pathfinding: Shortest path, all paths, Dijkstra, A - Centrality: PageRank, betweenness, closeness - Community detection: Louvain, label propagation - Similarity: Node similarity, Jaccard, overlap - Link prediction*: Predict future relationships

    Architecture¶

    Server-Based Deployment¶

    Unlike ChromaDB's embedded option, Neo4j always runs as a separate server process.

    Components: - Neo4j Server: Core database engine - Bolt Protocol: Binary protocol for client-server communication (port 7687) - HTTP API: RESTful API for management (port 7474) - Neo4j Browser: Web-based query interface

    Storage: - Write-Ahead Logging (WAL) for durability - Cache-heavy architecture (hot data in RAM) - Separate stores for nodes, relationships, properties, indexes

    Using Official Driver¶

    from neo4j import GraphDatabase

# Connect to Neo4j
driver = GraphDatabase.driver(
    "bolt://localhost:7687",
    auth=("neo4j", "password")
)

# Execute query
def find_best_encoder(tx, min_iso):
    query = """
    MATCH (tr:TrainingRun)-[:USES_MODEL]->(m:Model),
          (tr)-[:PRODUCED_CHECKPOINT]->(ckpt:Checkpoint),
          (tr)-[:TRAINED_ON]->(ds:Dataset)-[:CONTAINS_IMAGE]->(img:Image)
    WHERE img.exif_iso >= $min_iso
    RETURN m.encoder, AVG(ckpt.val_iou) as avg_iou
    ORDER BY avg_iou DESC
    LIMIT 5
    """
    result = tx.run(query, min_iso=min_iso)
    return [{"encoder": record["encoder"], "iou": record["avg_iou"]}
            for record in result]

# Execute in transaction
with driver.session() as session:
    results = session.execute_read(find_best_encoder, min_iso=800)
    print(results)

driver.close()

    Use ChromaDB When:¶

    ✅ You need semantic search ("what's similar?") ✅ Working with unstructured text (documentation, logs) ✅ Building RAG for LLMs ✅ Finding similar items by content ✅ Quick prototyping with minimal infrastructure ✅ Fuzzy matching is desired (different words, same meaning)

    Use Both When:¶

    ✅ Need semantic search AND relationship analysis ✅ Hybrid queries: "Find similar docs" → "How are they related?" ✅ Building comprehensive knowledge system ✅ Budget allows for dual infrastructure

    Why ChromaDB is Perfect: 

    # Simple integration with existing AIChatService
from chromadb import Client

class DocumentIndexer:
    def __init__(self, persist_directory: Path):
        self.client = Client(Settings(persist_directory=str(persist_directory)))
        self.collection = self.client.get_or_create_collection("crackz_docs")

    def index_documentation(self, docs_dir: Path):
        # Chunk markdown files by headings
        documents = []
        metadatas = []

        for md_file in docs_dir.glob("**/*.md"):
            chunks = self._chunk_by_heading(md_file)
            for chunk in chunks:
                documents.append(chunk.text)
                metadatas.append({
                    "source": str(md_file),
                    "section": chunk.heading,
                    "type": "documentation"
                })

        # Embed and index automatically
        self.collection.add(
            documents=documents,
            metadatas=metadatas,
            ids=[f"doc_{i}" for i in range(len(documents))]
        )

        if any(word in question_lower for word in ["how", "what", "explain", "guide", "documentation"]):

        if any(word in question_lower for word in ["best", "optimal", "which", "compare", "relationship"]):

        if "works best for" in question_lower or "optimal" in question_lower:

        if "does the documentation say" in question_lower:
            needs_vector = True

        return {
            "use_chromadb": needs_vector,
            "use_neo4j": needs_graph
        }

            model=self.model,
            max_tokens=2048,
            system=full_system_prompt,
            messages=[{"role": msg.role, "content": msg.content}
                     for msg in self.conversation_history]
        )

        return response.content[0].text

    async def _route_query(self, query: str) -> dict:
        """Determine which systems to query."""
        # Simple heuristic routing
        query_lower = query.lower()

        return {
            "use_rag": any(word in query_lower for word in ["how", "what", "documentation", "guide", "explain"]),
            "use_kg": any(word in query_lower for word in ["best", "optimal", "which", "compare", "performance"])
        }

    async def _execute_kg_queries(self, query: str, routing: dict) -> dict:
        """Execute appropriate knowledge graph queries."""
        results = {}

        # Pattern matching for specific query types
        if "best encoder" in query.lower():
            results["encoder_performance"] = self.kg_api.find_best_encoder_for_conditions()

        if "crack progression" in query.lower() or "worsened" in query.lower():
            # Extract GPS from query (simplified)
            results["crack_progression"] = self.kg_api.track_crack_progression()

        if "hyperparameter" in query.lower() or "optimal parameters" in query.lower():
            results["hyperparameters"] = self.kg_api.get_optimal_hyperparameters()

        return results

    Overhead and Complexity¶

    Pros of Hybrid: - ✅ Comprehensive answers (semantic + analytical) - ✅ Best tool for each job - ✅ Higher quality responses - ✅ More flexible query handling

    Cons of Hybrid: - ❌ 2x infrastructure (ChromaDB + Neo4j) - ❌ 2x query latency (even with parallelization) - ❌ More complex code (routing logic, aggregation) - ❌ Higher development cost (+2-3 weeks) - ❌ More operational overhead (2 systems to monitor)

    Cost Impact: - Development: +$20-45K (query router, aggregation, testing) - Infrastructure: +$65-500/month (Neo4j Aura) - Maintenance: +4-8 hours/month (monitoring both systems)

    Total Hybrid Cost (Year 1): - ChromaDB alone: $45-125K - Neo4j alone: $135-320K - Hybrid (both): $180-445K

    When Hybrid Makes Sense: - High query diversity (both semantic and analytical queries are frequent) - Budget allows for dual infrastructure - User needs justify the complexity - Team can support both systems

    Recommendation for Crackz: - Phase 1: Start with ChromaDB only - Phase 2: Evaluate after 3 months - Phase 3: Add Neo4j only if validated (hybrid usage becomes automatic)

    Decision Framework¶

    When to Use ChromaDB¶

    ✅ Always use ChromaDB if you need: - Semantic search over unstructured text - RAG for LLM applications - Finding similar documents/items by content - Quick prototyping with minimal infrastructure - Embedded database (no separate server)

    ✅ ChromaDB is the right choice when: - Data is primarily textual (docs, logs, summaries) - Queries are about similarity ("find related") - Relationships are implicit or simple - Budget is constrained - Need fast time-to-value

    ❌ Don't use ChromaDB for: - Complex relationship queries - Graph traversal (lineage, multi-hop) - Transactional updates across entities - Analytical aggregations across relationships

    When to Use Neo4j¶

    ✅ Always use Neo4j if you need: - Complex relationship analysis - Graph traversal (multi-hop queries) - Lineage tracking (parent-child chains) - Pattern detection in networks - Graph algorithms (centrality, community detection)

    ✅ Neo4j is the right choice when: - Data is highly interconnected - Relationships are first-class (as important as entities) - Queries involve "how are they connected?" - Need transactional consistency - Analytical queries across relationship paths

    ❌ Don't use Neo4j for: - Simple similarity search - Vector embeddings (use vector database) - Full-text search (use Elasticsearch) - Time-series metrics (use InfluxDB)

    When to Use Both (Hybrid)¶

    ✅ Use both ChromaDB + Neo4j when: - Need comprehensive knowledge system - Both semantic search AND relationship queries are frequent - Budget allows dual infrastructure - Query diversity justifies complexity - Users ask hybrid questions ("What's the best X, and what do docs say about it?")

    ⚠️ Consider hybrid carefully because: - 2x infrastructure complexity - Higher development and operational costs - Query routing logic required - May be overkill if one system covers 80% of needs

    Appendix: FAQ¶

    Q: Can I start with ChromaDB and add Neo4j later?¶

    A: Yes! This is the recommended approach (see Phase 1 → Phase 2 → Phase 3). Start with RAG, validate need, then add knowledge graph.

    Q: Will ChromaDB handle 1M+ vectors?¶

    A: Yes, but you'll need to use client-server mode or cloud mode instead of embedded mode. For Crackz's estimated 50-100K vectors, embedded mode is sufficient.

    Q: Can I use ChromaDB for relationship queries?¶

    A: No, not natively. You can use metadata filtering for simple relationships, but complex multi-hop queries require a graph database.

    Q: Is Neo4j free?¶

    A: The Community Edition is free (open-source), but lacks clustering and some enterprise features. Desktop is free for development. Aura (cloud) has a free tier with limitations. Enterprise Edition requires licensing.

    Q: How do I migrate from ChromaDB to another vector database?¶

    A: ChromaDB supports export to standard formats. Most vector databases have import tools. Migration is relatively straightforward (export embeddings, re-import).

    Q: How do I migrate from NetworkX to Neo4j?¶

    A: NetworkX can export to JSON or GraphML formats. Neo4j can import these via LOAD CSV or APOC procedures. Design your NetworkX schema with future Neo4j migration in mind.

    Q: What's the minimum hardware for Neo4j?¶

    A: 4GB RAM, 2 CPU cores, 10GB storage for small deployments. Recommended: 16GB RAM, 4 cores, 50GB+ storage for production.

    Q: Can I run Neo4j and ChromaDB on the same machine?¶

    A: Yes! They use different ports and resources. A machine with 16GB RAM can comfortably run both for small-medium workloads.

    Q: What happens if my query needs both semantic search AND graph traversal?¶

    A: Use the hybrid architecture described in this document. Query both systems in parallel, aggregate results, then use an LLM to generate a comprehensive answer.

    Q: How much does it cost to embed 100K documents?¶

    A: With OpenAI text-embedding-3-small: 100K docs × avg 200 tokens = 20M tokens × $0.00002/1K = $0.40. Very cheap. You can also use free local models like Sentence Transformers.
