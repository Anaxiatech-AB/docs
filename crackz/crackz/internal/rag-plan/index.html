    RAG Issues Inventory & Solution Options¶

    Created: 2026-05-07. Tracks the current state of AI chat context injection and the path toward full RAG.

    Issue Inventory¶

    Bug 1 — _get_context() was returning "" (resolved by this PR)¶

    File: gui/src/crackz_gui/services/ai_chat.py:287–344

    project_context was built correctly (project name, image counts, backbone, checkpoints) but was never appended to context_parts. The wiring to inject context into the system prompt already existed, but the if context: guard was always false. This PR appends the project context before returning from _get_context().

    Bug 2 — Registry DB was not queried from _get_context() (resolved by this PR)¶

    Files: core/src/crackz/ai/model/registry.py, core/src/crackz/ai/model/persistence/metrics_store.py

    The per-project project.db (project.registry_db_path) already stores: - training_epochs — per-epoch train_loss, val_loss, val_iou, val_acc, run_id - detection_runs — image_count, crack_count, avg_confidence, threshold, run_at - models — model history

    ModelRegistry already exposes get_latest_detection_stats() and get_best_val_iou(), both ready to call. _get_context() previously only globbed checkpoint files, so the SQLite data was present but not surfaced to the AI. This PR routes the GUI through the app-layer get_project_registry_metrics() helper so registry access and legacy DB migration stay outside the GUI service.

    Gap 3 — No document search (45+ markdown docs, ~17K lines)¶

    No mechanism to retrieve relevant doc sections for a query. Full injection would exceed context window budgets.

    Gap 4 — Static system prompt¶

    _build_system_prompt() (line 613) is a fixed string with no dynamic project state or history.

    Immediate Fix (Bug 1 + Bug 2)¶

    Scope: Add context assembly in _get_context() and route registry metrics through the app layer. No new dependencies.

    Change 1 — Append the project context that's already built (line 343): 

    context_parts.append(project_context)

    Change 2 — Query app-layer registry metrics for training and detection history: 

    from crackz.app.models import get_project_registry_metrics

metrics = get_project_registry_metrics(project)
if metrics.has_metrics:
    metrics_context = "## Training & Detection History\n"
    if metrics.best_val_iou is not None:
        metrics_context += f"- **Best Validation IoU:** {metrics.best_val_iou:.4f}\n"
    if metrics.latest_detection_image_count:
        metrics_context += (
            f"- **Latest Detection Run:** {metrics.latest_detection_image_count} images, "
            f"{metrics.latest_detection_crack_count} cracks found"
        )
        if metrics.latest_detection_avg_confidence is not None:
            metrics_context += f", avg confidence {metrics.latest_detection_avg_confidence:.3f}"
        metrics_context += "\n"
    context_parts.append(metrics_context)

    Solution Options (Future Phases)¶

    Option A — Structured injection only (immediate fix above)¶

    Pros: Zero new deps, covers "What's my project's status?" and "What was my best IoU?"
    Cons: No doc search, no cross-project analytics

    Option B — SQLite FTS5 for doc search¶

    Extend chat_history.db with an FTS5 virtual table. Chunk 45+ markdown docs at startup, keyword-search top-3 chunks per query.
    Pros: Zero new deps (SQLite FTS5 stdlib), fast, deterministic, offline
    Cons: Keyword-only, docs must be re-indexed after updates
    Effort: ~1 week

    Option C — ChromaDB + local embeddings (original roadmap plan, issues #311–315)¶

    Embed docs and training history with sentence-transformers + ChromaDB embedded store.
    Pros: True semantic search, scales to 50+ projects, cites sources
    Cons: +50–150MB deps, cold-start indexing, background thread in Qt app, 4–6 weeks
    Decision point: Only if Option B keyword search misses content regularly

    Option D — Anthropic prompt caching for docs¶

    Bundle docs as a cached cache_control: ephemeral system prompt prefix.
    Pros: No vector DB
    Cons: Anthropic-only, 5-min TTL re-caches per session, ~250K tokens

    Recommended sequence: Immediate fix → Option B if "How do I...?" tickets remain high → Option C if semantic gaps are demonstrable.
