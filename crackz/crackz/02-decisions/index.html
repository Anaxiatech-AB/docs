    Architecture Decisions¶

    Key technical decisions and their rationale (ADR-style)

    This document records important architecture decisions made during Crackz development. Each decision includes context, the decision itself, and consequences.

    Format¶

    Each decision follows this structure: - Context: Why we needed to make a decision - Decision: What we chose - Consequences: Trade-offs and implications - Status: Active | Deprecated | Superseded

    ADR-001: Use uv for Dependency Management + hatchling for Builds¶

    Context: Python package management is slow with pip and complex with poetry. Additionally, setuptools as a build backend is aging and lacks modern features.

    Decision: Use a hybrid approach: - uv (Astral's package manager) for dependency management, lockfiles, and task execution - hatchling (PyPA-official build backend) for building wheels and sdists

    Consequences: - ✅ 10-100x faster installs compared to pip (via uv) - ✅ Automatic virtual environment management (via uv) - ✅ Built-in lockfile support via uv.lock (deterministic builds) - ✅ Modern PEP 517-compliant build backend (hatchling) - ✅ Better build defaults (uses .gitignore for sdist) - ✅ Preserves custom PyTorch index routing (uv feature) - ✅ Compatible with python-semantic-release for versioning - ⚠️ Two tools instead of one (but clear separation of concerns) - ⚠️ Relatively new toolchain (requires team adoption)

    Status: Active (Updated 2025-11-30)

    Related: .github/workflows/, pyproject.toml, Dockerfile*, all documentation

    Migration Notes: - Migrated from setuptools to hatchling in v0.67.0 - All existing uv configuration preserved (PyTorch routing unchanged) - Semantic versioning still managed by python-semantic-release

    ADR-002: PyTorch Lightning for ML Pipeline¶

    Context: Raw PyTorch requires significant boilerplate for training loops, checkpointing, and distributed training.

    Decision: Use PyTorch Lightning as the ML framework layer.

    Consequences: - ✅ Production-ready training with minimal boilerplate - ✅ Built-in checkpointing, logging, and callbacks - ✅ Easy GPU/multi-GPU scaling - ✅ TensorBoard integration out of the box - ⚠️ Additional abstraction layer to learn - ⚠️ Opinionated structure (less flexibility)

    Status: Active

    Related: src/crackz/ai/training.py, src/crackz/ai/models.py

    ADR-003: Typer for CLI Framework¶

    Context: Need type-safe CLI with good DX, auto-generated help, and modern Python features.

    Decision: Use Typer instead of Click or argparse.

    Consequences: - ✅ Type hints drive CLI interface (DRY principle) - ✅ Excellent auto-generated help text - ✅ Easy to test and maintain - ✅ Built on Click (mature foundation) - ⚠️ Less flexible than raw Click for complex UIs - ⚠️ Learning curve for developers used to argparse

    Status: Active

    Related: src/crackz/cli/, all CLI commands

    ADR-004: CustomTkinter for GUI (Not Qt)¶

    Context: Need lightweight desktop GUI. Qt requires commercial licensing for proprietary software; Tkinter is too basic.

    Decision: Use CustomTkinter (modern Tkinter wrapper) instead of Qt or Kivy.

    Consequences: - ✅ No licensing costs (compatible with GPL-3.0) - ✅ Modern dark mode support - ✅ Lightweight (~1MB vs Qt's ~50MB) - ✅ Easy to package with PyInstaller - ⚠️ Less feature-rich than Qt - ⚠️ Limited third-party widgets - ⚠️ Known issue: some customers want Qt migration (#127)

    Status: Active (Qt migration under consideration)

    Related: src/crackz/gui/, issue #127

    ADR-005: Pydantic v2 for Configuration¶

    Context: Need type-safe config validation with YAML serialization. Manual validation is error-prone.

    Decision: Use Pydantic v2 models for all configuration with YAML backend.

    Consequences: - ✅ Type-safe validation at load time - ✅ Auto-generated JSON schemas - ✅ Excellent error messages for invalid configs - ✅ Easy to extend and version (schema_version field) - ⚠️ YAML library dependency (pyyaml) - ⚠️ Learning curve for Pydantic's API

    Status: Active

    Related: src/crackz/config/, project YAML files

    ADR-006: Hybrid Logging Architecture¶

    Context: Need system-wide logs for debugging AND per-project logs for customer audit trails.

    Decision: Implement hybrid logging with: - Central log sink (pre-project operations, global context) - Per-project log sink (project-specific operations)

    Consequences: - ✅ Complete audit trail per project - ✅ System-wide logging for debugging - ✅ Flexible central log location (env var, flag, or temp) - ⚠️ Slightly more complex logging setup - ⚠️ Two log locations to manage

    Status: Active

    Related: src/crackz/log/, CRACKZ_LOG_DIR env var

    ADR-007: Centralized CLI Options Pattern¶

    Context: CLI option definitions were duplicated across modules (e.g., multiple FORCE_OPTION definitions).

    Decision: Centralize all reusable CLI options in src/crackz/cli/options.py.

    Consequences: - ✅ Single source of truth for option definitions - ✅ Consistent help text and behavior - ✅ Easy to update globally - ⚠️ Requires discipline to import (not re-define) - ⚠️ One-time refactoring effort to consolidate

    Status: Active

    Related: src/crackz/cli/options.py, all CLI commands

    ADR-008: Conventional Commits for Versioning¶

    Context: Manual versioning and changelog generation is error-prone and time-consuming.

    Decision: Use conventional commits (feat:, fix:, etc.) with semantic-release for automated versioning.

    Consequences: - ✅ Automatic version bumps (major, minor, patch) - ✅ Auto-generated changelog from commits - ✅ Clear commit history for code review - ⚠️ Team must follow commit conventions - ⚠️ Bad commit messages affect release notes

    Status: Active

    Related: .releaserc.yml, GitHub Actions workflows

    ADR-009: Three Docker Variants (Full, Slim, GPU)¶

    Context: Different deployment scenarios need different image sizes and capabilities.

    Decision: Provide three Dockerfiles: - Dockerfile: Balanced full-featured image - Dockerfile.slim: Minimal runtime (no dev tools) - Dockerfile.gpu: CUDA runtime for GPU workloads

    Consequences: - ✅ Optimized images for each use case - ✅ Faster pulls for slim (smaller size) - ✅ GPU support without bloating CPU images - ⚠️ Three Dockerfiles to maintain - ⚠️ Need clear documentation on which to use

    Status: Active

    Related: Dockerfile, Dockerfile.slim, Dockerfile.gpu, Makefile

    ADR-010: uv sync in Docker (Not Wheel Builds)¶

    Context: Building wheels in Docker is slow and complex. uv sync is faster and simpler.

    Decision: Use uv sync directly in Docker images instead of pre-built wheels.

    Consequences: - ✅ Faster Docker builds (uv's speed) - ✅ Simpler Dockerfile (no multi-stage wheel building) - ✅ Consistent with local development workflow - ⚠️ Requires uv installed in base image - ⚠️ Build cache depends on pyproject.toml + uv.lock

    Status: Active

    Related: All Dockerfiles

    ADR-011: Ruff for Linting and Formatting¶

    Context: Traditional Python linting (flake8, black, isort) requires multiple tools and is slow.

    Decision: Use Ruff for both linting and formatting (replaces black, isort, flake8, etc.).

    Consequences: - ✅ 10-100x faster than traditional tools - ✅ Single tool for linting + formatting - ✅ Compatible with existing configs (black, isort rules) - ✅ Excellent VS Code integration - ⚠️ Newer tool (less mature than black) - ⚠️ Some edge cases in AST-based fixes

    Status: Active

    Related: pyproject.toml (Ruff config), pre-commit hooks

    ADR-012: 75% Minimum Test Coverage¶

    Context: Need quality gates without over-constraining development. 100% is unrealistic; <70% is too low.

    Decision: Enforce 75% minimum test coverage in CI (target 85%).

    Consequences: - ✅ Catches most untested code paths - ✅ Realistic target for teams - ✅ Enforced automatically in CI - ⚠️ Can be gamed with trivial tests - ⚠️ Doesn't measure test quality

    Status: Active

    Related: pyproject.toml (pytest-cov config), CI workflows

    ADR-013: Performance Regression Tests with Benchmarks¶

    Context: Performance regressions are hard to catch without automated measurement.

    Decision: Use pytest-benchmark with automated regression detection (>20% mean, >30% max).

    Consequences: - ✅ Catches performance regressions before merge - ✅ Historical performance tracking - ✅ Baseline updates after intentional changes - ⚠️ Benchmark stability depends on CI environment - ⚠️ Requires baseline management

    Status: Active

    Related: tests/unit/benchmarks/, .benchmarks/ (gitignored)

    ADR-014: Project Schema Versioning with Migrations¶

    Context: Project YAML format evolves over time. Breaking old projects is unacceptable for customers.

    Decision: Add schema_version field to project configs with migration system.

    Consequences: - ✅ Backward compatibility for customer projects - ✅ Explicit migration path for breaking changes - ✅ Safe upgrades (creates .bak files) - ⚠️ Migration code must be maintained - ⚠️ Testing migrations requires old project fixtures

    Status: Active

    Related: crackz migrate, src/crackz/config/, schema_version field

    ADR-015: typer.secho() for User Messages, logger for Technical Info¶

    Context: Mixed output methods (print, echo, console.print) created inconsistent UX.

    Decision: Standardize on: - typer.secho() with colors for end-user messages - logger for technical/operational information - NEVER use print(), typer.echo(), or console.print()

    Consequences: - ✅ Consistent user experience across all CLI commands - ✅ Clear separation: user messages vs operational logs - ✅ Better testability (can capture typer output) - ⚠️ Requires team discipline to follow conventions - ⚠️ One-time refactoring effort to standardize existing code

    Status: Active (strictly enforced)

    Related: All CLI commands, CONTRIBUTING.md, DEVELOPMENT_STANDARDS.md

    ADR-016: GitHub Actions for CI/CD¶

    Context: Need reliable, cloud-based CI/CD with good GitHub integration.

    Decision: Use GitHub Actions exclusively (no Travis, CircleCI, etc.).

    Consequences: - ✅ Native GitHub integration (PRs, issues, releases) - ✅ Free for public repos, generous for private - ✅ Good ecosystem of third-party actions - ✅ Matrix builds for multi-platform testing - ⚠️ Vendor lock-in to GitHub - ⚠️ YAML workflow syntax (learning curve)

    Status: Active

    Related: .github/workflows/

    ADR-017: MCP (Model Context Protocol) Integration¶

    Context: AI assistants (Claude, Copilot) need standardized access to development tools.

    Decision: Implement MCP integration with crackz mcp init command.

    Consequences: - ✅ Standardized AI assistant integration - ✅ Fine-grained permission control - ✅ Future-proof for AI-powered development - ⚠️ Relatively new protocol (evolving spec) - ⚠️ Limited ecosystem currently

    Status: Active

    Related: src/crackz/cli/mcp_cli.py, .mcp/config.json

    ADR-018: GPS/EXIF Support with GeoJSON Export¶

    Context: Harbor inspections often have GPS-tagged photos. Customers need location-based reports.

    Decision: Add GPS extraction from EXIF, interactive maps (Folium), and GeoJSON export.

    Consequences: - ✅ Location-aware detection results - ✅ Interactive HTML maps for visual reporting - ✅ GeoJSON export for GIS integration - ⚠️ Not all images have GPS data (graceful fallback) - ⚠️ Privacy considerations (GPS data in exports)

    Status: Active

    Related: crackz geo commands, src/crackz/geo/
