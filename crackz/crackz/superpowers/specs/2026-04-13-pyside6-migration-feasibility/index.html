    Feasibility Study: CustomTkinter → PySide6 Migration¶

    Date: 2026-04-13 Status: Draft — awaiting approval Scope: Full GUI layer rewrite. Business logic untouched. Platforms: Windows, macOS, Linux

    1. Executive Summary¶

    The crackz desktop GUI is built on CustomTkinter (~22K lines, 99 files, 32 screens). Four concrete pain points drive this study: poor look & feel, missing widget capabilities, canvas rendering performance, and packaging friction with PyInstaller/Nuitka.

    Recommendation: Proceed. All four pain points have direct PySide6 solutions. The business logic layer is cleanly separated, making this a GUI-layer-only rewrite with no risk to the AI pipeline. Honest effort estimate is 740–1,055 engineering hours (4–7 months solo; 2.5–4 months with two developers).

    Stack: PySide6 (LGPL, official Qt binding) + QWidget paradigm + QGraphicsView for image-heavy views.

    2. Current State¶

    Metric Value
    GUI source files 99 Python files
    Total GUI lines ~22,000
    Distinct screens / dialogs 32
    CTk widget usages 1,049
    Largest single file mask_editor.py — 800 lines
    Mixed non-CTk widgets ttk.Treeview, tk.Menu, matplotlib.FigureCanvasTkAgg
    Threading model asyncio loop in daemon thread + worker threads, tk.after() for GUI updates
    External GUI libs PIL/Pillow, matplotlib, watchdog, diskcache

    The services/ layer in src/crackz/gui/services/ provides a clean interface between GUI and business logic. No GUI code exists in src/crackz/ai/ or src/crackz/config/. This separation is the key enabler for migration.

    3. Motivation → Qt Solution Mapping¶

    3a. Look & Feel¶

    • Qt Fusion style + QSS dark stylesheet → professional, consistent cross-platform appearance
    • QPalette honours OS-level dark/light mode toggle automatically
    • Frame-rate independent rendering — no more Tkinter resize flicker
    • Per-platform native rendering: Windows Fusion/Win32, macOS Cocoa, Linux X11/Wayland

    3b. Missing Widgets¶

    Pain (current) Solution (PySide6) Key gain
    ttk.Treeview — no checkboxes, no drag-drop QTreeView + custom model Checkboxes, drag-drop, inline edit, virtual scroll
    CTkScrollableFrame gallery — renders all items QListView / QTableView with QAbstractItemModel Virtual rendering — only visible rows paint
    CTkCanvas mask editor — full bitmap repaint QGraphicsView / QGraphicsScene GPU compositing, arbitrary zoom, scene graph
    CTkTextbox — no rich text QTextEdit Rich text, syntax highlight, find/replace
    CTkTabview QTabWidget Detachable tabs, overflow menu
    tk.Menu — no icons/shortcuts QMenuBar + QAction Icons, keyboard shortcuts, checkable items
    No docking QDockWidget Detachable chat window, detachable browser pane
    No resizable panes QSplitter Drag-to-resize browser ↔ content area

    3c. Performance¶

    • QGraphicsView uses OpenGL for compositing — mask editor stroke repaint becomes a scene graph dirty-region update, not a full bitmap redraw
    • QListView virtual rendering makes a 10,000-image gallery cost the same as a 10-image one
    • QPixmap / QImageReader — hardware-accelerated, automatic EXIF orientation, no PIL-to-ImageTk conversion needed for display
    • Qt layout engine is C++-native; widget geometry is faster than Tkinter's Python-side manager

    3d. Packaging¶

    • PySide6 ships official PyInstaller hooks in the package itself (__pyinstaller/)
    • pyside6-deploy wrapper tool for PyInstaller/Nuitka specifically
    • Qt plugin discovery (platform, imageformat) is well-understood by packaging tools — no manual --add-binary flags
    • arm64 macOS fully supported via official PySide6 wheels

    4. Recommended Stack¶

    Component Choice Reason
    Qt binding PySide6 LGPL 3.0 — commercial distribution free. Official Qt Company.
    UI paradigm QWidget Direct 1:1 migration path from CTk. Full Python. Solves all 4 pain points.
    Image views QGraphicsView / QGraphicsScene GPU-composited. Replaces CTkCanvas in mask editor, gallery, batch review, uncertainty viewer.
    Charts matplotlib.FigureCanvasQTAgg Drop-in swap of the Tkinter backend. 1-line change per embed.
    Styling QSS CSS-like, dark theme, brand colours, per-widget overrides.
    File watcher watchdog (keep) Just swap tk.after() callbacks → QTimer.singleShot() or Qt signals.
    Packaging PyInstaller + PySide6 hooks Better than CTk; pyside6-deploy as optional wrapper.

    QML is not recommended. It doubles the effort (800–1,000h vs 740–1,055h full range), requires learning a new language, and the Python↔QML bridge adds state management complexity. QWidget alone solves all four pain points at lower cost. QML can be revisited for specific views (e.g. detection gallery) after the QWidget migration is stable.

    5. What We Lose / Risks¶

    Item Impact Mitigation
    CTk built-in dark theme Low QSS replacement is more powerful; write once, reuse everywhere
    CTkImage auto-DPI scaling Low Qt handles HiDPI natively via devicePixelRatio; remove CTkImage wrappers
    StringVar / BooleanVar reactive bindings Medium Systematic: each StringVar.trace() → Qt signal
    tk.after() thread-safety pattern Medium Qt signals emitted from non-GUI threads auto-queue to GUI thread
    diskcache storing CTkImage objects Low Swap cache value type to QPixmap; same LRU logic
    Existing GUI tests Medium Review test suite; most unit tests cover business logic, not widgets
    Developer Qt ramp-up Medium QWidget API is well-documented; ~1–2 weeks to productive speed

    Highest-Risk Component: asyncio ↔ Qt event loop bridge¶

    src/crackz/gui/async_helpers.py currently runs asyncio.new_event_loop() in a daemon thread and uses tk.after() to post GUI updates. The Qt equivalent:

    asyncio.new_event_loop() in QThread
    → CallbackDispatcher (unchanged — lives in business logic layer)
    → Emit Qt signals from worker thread → auto-queued to GUI thread
    → Slot on widget handles update

    PySide6 signals emitted from non-GUI threads are automatically queued — this is the precise equivalent of tk.after(0, callback). The create_threadsafe_gui_callback() helper becomes a signal emit. This is well-documented PySide6 territory. Estimated at 40–60h; it's the single most careful rewrite.

    7. Platform Notes¶

    Platform Qt Backend Packaging Extra overhead

    Linux X11 + Wayland AppImage or flatpak ~15–20h (xcb platform plugin + OpenGL in bundle)

    8. Migration Sequence (if approved)¶

    1. Phase 0 spike — 2-week timebox. Build main window shell + dark QSS + one real panel (e.g. ProjectSummaryView). Validates approach and calibrates effort before committing to full migration.
    2. Phase 1 — Foundation shell. All other panels render inside it.
    3. Phase 2 — Standard panels, in rough order: simple dialogs first, then views, then complex multi-file panels.
    4. Phase 3 — Image-heavy views. QGraphicsView pattern established in spike.
    5. Phase 4 — Polish, platform testing, packaging.

    Work on a feat/pyside6-migration long-lived branch. Keep main shipping CTk throughout the migration. Merge only when Phase 4 passes.

    10. Verdict¶

    Go — with a 2-week Phase 0 spike as gate.

    The business logic is cleanly separated, the Qt solutions are direct, and all four pain points are addressed by QWidget alone. The effort is proportionate to a commercial product with a multi-year lifespan.

    The spike (Phase 0) is not optional — it validates effort assumptions and produces the QSS stylesheet and async bridge pattern that all other phases depend on. Approve Phase 0; re-evaluate full scope after the spike.

    If deferred: The two highest-value targeted fixes are (a) replacing the mask editor canvas with QGraphicsView in isolation — this is the biggest performance win — and (b) switching packaging to pyside6-deploy even before full migration. Both are possible as standalone tasks without committing to a full rewrite.
