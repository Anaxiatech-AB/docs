    Release Control Plan¶

    Plan for adding human approval gates and tighter branch controls to Crackz releases, without replacing the current Commitizen-based versioning.

    Problem Statement¶

    The current release flow is too automatic for the volume of small commits landing on main. A broken change can become a public release before there is a clear human checkpoint.

    Current State¶

    release.yml already has two paths:

    • Auto path — triggered when integration tests pass on main: commitizen bumps the version, builds wheel artifacts, and publishes a GitHub release automatically. There is no human approval step on this path.
    • Manual path — workflow_dispatch with a free-text YES confirmation input. This is bypassable and leaves no audit trail.

    PyInstaller executables (pyinstaller-build.yml) and Docker images (docker-build.yml) are separate, manually triggered workflows and are not part of the release gate problem.

    Goal¶

    • Keep fast, small commits on feature branches.
    • Prevent broken work from becoming a public release.
    • Add an explicit, auditable approval step before a release is published.
    • Keep the current Commitizen-based versioning.
    • Define "publication" as: creating and publishing the GitHub release (tag, changelog, wheel artifacts). PyInstaller and Docker builds remain separate and out of scope.

    Proposed Direction¶

    1. Separate merge from publish¶

    Current behavior effectively treats merge-to-main as publish-to-customers.

    Target behavior:

    • Merge to main triggers version bump and artifact build (prepare).
    • A draft GitHub release is created automatically.
    • A maintainer explicitly approves before the draft is promoted to published.

    2. Add a release gate via GitHub protected environment¶

    Use a GitHub protected environment named release with required reviewers.

    • Enforced by GitHub — not an honor system.
    • Creates an audit trail (who approved, when).
    • Implemented by adding environment: release to the publish job in release.yml.
    • The existing workflow_dispatch YES input becomes redundant and should be removed.

    The release.yml job split becomes:

    Job Trigger What it does
    prepare auto (integration tests pass) commitizen bump, build artifacts, create draft release
    publish after prepare, environment: release human approves → draft promoted to published

    3. Tighten main branch protection¶

    Require:

    • Passing status checks: CI / lint, CI / test, integration / run
    • At least 1 reviewer approval
    • No direct pushes; no force-pushes
    • Squash merge only
    • Branch must be up-to-date before merging

    4. Enforce conventional commits at the PR level¶

    Add a CI step that runs cz check against the PR title. Because squash merges use the PR title as the commit message, this ensures the commit that lands on main follows the conventional format — without relying on every intermediate branch commit.

    5. Make release readiness explicit¶

    Surface the checklist at the release environment approval step (embed it in the environment description or as a pinned comment on the draft release):

    • CI green
    • Integration tests green
    • Changelog entry reviewed
    • Version bump is expected (feat / fix / perf)
    • Artifact filenames match bumped version

    6. Hotfix path¶

    Urgent fixes that cannot wait for the normal gate:

    • Use workflow_dispatch on release.yml with a mandatory reason input.
    • Environment admins can approve the release environment immediately (GitHub built-in).
    • Alternatively, a hotfix/* branch can skip the integration-test gate and go directly to the release environment approval.

    7. Keep release generation deterministic¶

    Continue using Commitizen for versioning and changelog generation. The squash commit message (= PR title) is the single trigger source. Ad hoc branch commits do not define release behavior.

    Phased Implementation Plan¶

    Phase Work Effort
    1 Document the policy (this file) Docs only
    2 Add main branch protection rules (specific checks, 1 reviewer, squash) GitHub settings
    3 Create release GitHub environment; split release.yml prepare/publish jobs ~1 h
    4 Add PR-title conventional commit check to CI ~30 min
    5 Embed release checklist in environment description / workflow summary ~30 min
    6 Update contributor docs, PR template, workflow reference Docs

    Phase 1: Document the policy¶

    • This file is the policy document.
    • Clarify when a release is prepared (automatic) and who can publish it (maintainer via environment approval).

    Phase 2: Add branch protection¶

    • Enforce the checks and reviewer requirement listed in Section 3 above.
    • Block direct pushes and force-pushes.
    • Standardize on squash merge.

    Phase 3: Split prepare vs publish¶

    • Rename / split the release job in release.yml.
    • prepare job: commitizen bump, artifact build, draft release creation.
    • publish job: needs: prepare, environment: release — requires human approval before promoting draft to published.
    • Remove the workflow_dispatch YES confirmation (replaced by environment gate).

    Phase 4: PR-title commit check¶

    • Add a cz check step to an existing CI workflow that validates the PR title on every pull_request event targeting main.

    Phase 5: Release checklist¶

    • Add checklist items to the release environment description in GitHub repository settings.
    • Optionally surface them in the workflow-summary job output so they are visible at approval time.

    Phase 6: Update docs¶

    • Update contributor guidance (branching, PR titles, merge strategy).
    • Update workflow reference docs.

    Recommended End State¶

    1. Feature branches can still have small commits.
    2. PRs must pass CI + integration tests and get 1 reviewer approval before merge.
    3. Merging to main automatically prepares a release (version bump, artifacts, draft).
    4. A maintainer approves publication via the release GitHub environment.
    5. The published release includes tag, CHANGELOG entry, and all wheel artifacts.
    6. Hotfixes bypass the integration-test gate via workflow_dispatch with a reason; an environment admin approves immediately.

    Out of Scope For Now¶

    • Replacing Commitizen.
    • Introducing a long-lived release branch.
    • Reworking the entire CI/CD layout.
    • Changing artifact formats or distribution channels.
    • PyInstaller and Docker build automation (already separate workflows).
